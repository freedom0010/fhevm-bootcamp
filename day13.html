The Handle Model Revisited

An FHEVM handle is a uint256 that uniquely identifies a ciphertext stored in the coprocessor. The handle itself is public — it's safe to pass between contracts, store in mappings, and emit in events. The ciphertext behind the handle is never on-chain.

The critical constraint: a contract can only operate on a handle if the ACL has granted it permission. Passing a handle to a contract without granting permission means the receiving contract cannot compute on it.

Passing Handles Between Contracts

Solidity
Concept — handle as uint256
// Handles are just uint256 values — safe to pass anywhere
interface IEncryptedVault {
    // Returns the raw uint256 handle (NOT the ciphertext)
    function getBalanceHandle(address user) external view returns (uint256);
}

contract Router {
    IEncryptedVault vault;

    function route(address from, address to) external {
        // Get the handle for the sender's balance
        uint256 handle = vault.getBalanceHandle(from);

        // Wrap back as euint64 to operate on it
        // ⚠️  This only works if vault has called allowTransient(handle, address(this))
        euint64 balance = euint64.wrap(handle);
        // ...
    }
}

ACL in Cross-Contract Calls

When Contract A calls Contract B and passes a handle, Contract B needs ACL permission to compute on that handle. There are two ways to grant it:

MethodScopeWhen to Use
TFHE.allowTransient(handle, addr) Current transaction only — permission is not stored permanently Composability within a single transaction (e.g., token router calling escrow in the same tx)
TFHE.allow(handle, addr) Persistent — stored in ACL contract state permanently Long-lived grants: a contract that needs to access a value across multiple transactions

Transient vs Persistent Permissions

allowTransient — Single Transaction

Solidity
contracts/ConfidentialERC20.sol (transfer)
/**
 * @dev Transfer with transient ACL grant to the recipient contract.
 *      allowTransient grants permission only for the current tx.
 *      The recipient (if a contract) can compute on the ciphertext
 *      during the same call chain, but not in future transactions.
 */
function transfer(
    address to,
    bytes32 encryptedAmount,
    bytes calldata inputProof
) external returns (bool) {
    euint64 amount = TFHE.asEuint64(encryptedAmount, inputProof);

    euint64 newBalanceSender = TFHE.sub(_balances[msg.sender], amount);
    euint64 newBalanceRecipient = TFHE.add(_balances[to], amount);

    _balances[msg.sender] = newBalanceSender;
    _balances[to]         = newBalanceRecipient;

    // Persistent ACL: sender and recipient can always access their balance
    TFHE.allow(newBalanceSender,    msg.sender);
    TFHE.allow(newBalanceRecipient, to);

    // Allow THIS contract to access both balances (for future operations)
    TFHE.allow(newBalanceSender,    address(this));
    TFHE.allow(newBalanceRecipient, address(this));

    // Transient: if 'to' is a contract, it can use the handle in THIS tx only
    TFHE.allowTransient(newBalanceRecipient, to);

    emit Transfer(msg.sender, to);
    return true;
}

allow — Persistent Grant

Solidity
contracts/Escrow.sol (accept deposit)
/**
 * @dev Escrow accepts a deposit. The deposited amount needs a
 *      PERSISTENT allow so the escrow can access it in future txs
 *      (e.g., when releasing funds to the beneficiary).
 */
function deposit(
    address beneficiary,
    euint64 amount          // already ACL-allowed to this contract via allowTransient
) external {
    _deposits[msg.sender][beneficiary] = amount;

    // Persistent: escrow needs to access this in future release() calls
    TFHE.allow(amount, address(this));

    // Optional: let beneficiary verify the deposit exists (cannot read value)
    TFHE.allow(amount, beneficiary);

    emit Deposited(msg.sender, beneficiary);
}
⚠
allowTransient Does Not Persist
If you use allowTransient and a later transaction needs access to the same handle, it will fail with an ACL error. Use allow whenever the receiving contract needs multi-transaction access.

Pattern: Encrypted Token Router

A router accepts tokens from one contract and forwards them to another. The key challenge: the router needs transient permission to read the incoming handle, compute the routing logic, and then pass the resulting handle to the destination.

Router Implementation

Solidity
contracts/EncryptedRouter.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "fhevm/lib/TFHE.sol";

interface IConfidentialToken {
    function transferFrom(address from, address to, bytes32 handle, bytes calldata proof) external;
    function getBalanceHandle(address user) external view returns (uint256);
}

interface IEncryptedVault {
    function depositFrom(address user, euint64 amount) external;
}

contract EncryptedRouter {
    IConfidentialToken public immutable token;
    IEncryptedVault    public immutable vault;

    constructor(address _token, address _vault) {
        token = IConfidentialToken(_token);
        vault = IEncryptedVault(_vault);
    }

    /**
     * @dev Route: transfer tokens from user → router → vault in one tx.
     *      Step 1: Token contract grants router transient permission.
     *      Step 2: Router passes the handle to vault with allow().
     */
    function routeToVault(
        bytes32 encryptedAmount,
        bytes calldata inputProof
    ) external {
        // Step 1: Transfer tokens to this router contract (token grants allowTransient)
        token.transferFrom(msg.sender, address(this), encryptedAmount, inputProof);

        // Step 2: Get the handle this contract now owns
        uint256 handle = token.getBalanceHandle(address(this));
        euint64 routerBalance = euint64.wrap(handle);

        // Step 3: Grant vault PERSISTENT access before calling it
        TFHE.allow(routerBalance, address(vault));

        // Step 4: Deposit into vault
        vault.depositFrom(msg.sender, routerBalance);
    }
}

Pattern: Encrypted DeFi Escrow

An escrow holds encrypted funds until a condition is met (e.g., a service is delivered and both parties confirm). The escrow must maintain persistent ACL access to the deposited handles, and the release logic must be oblivious (using TFHE.select).

Escrow Contract

Solidity
contracts/EncryptedEscrow.sol
contract EncryptedEscrow {
    struct Deal {
        euint64  amount;
        address  buyer;
        address  seller;
        ebool    buyerConfirmed;
        ebool    sellerConfirmed;
        bool     released;
    }

    mapping(uint256 => Deal) private _deals;
    uint256 private _nextDealId;

    function createDeal(address seller, euint64 amount) external returns (uint256 dealId) {
        dealId = _nextDealId++;
        _deals[dealId] = Deal({
            amount: amount,
            buyer: msg.sender,
            seller: seller,
            buyerConfirmed: TFHE.asEbool(false),
            sellerConfirmed: TFHE.asEbool(false),
            released: false
        });
        // Escrow must have persistent access to operate on amount later
        TFHE.allow(amount, address(this));
    }

    function confirm(uint256 dealId) external {
        Deal storage d = _deals[dealId];
        require(!d.released, "Already released");

        if (msg.sender == d.buyer) {
            d.buyerConfirmed = TFHE.asEbool(true);
            TFHE.allow(d.buyerConfirmed, address(this));
        } else if (msg.sender == d.seller) {
            d.sellerConfirmed = TFHE.asEbool(true);
            TFHE.allow(d.sellerConfirmed, address(this));
        }
    }

    function release(uint256 dealId) external {
        Deal storage d = _deals[dealId];
        require(!d.released);

        // Compute: bothConfirmed = buyerConfirmed AND sellerConfirmed
        ebool bothConfirmed = TFHE.and(d.buyerConfirmed, d.sellerConfirmed);

        // Oblivious release: amount goes to seller if both confirmed, else stays
        euint64 toSeller = TFHE.select(bothConfirmed, d.amount, TFHE.asEuint64(0));
        euint64 toBuyer  = TFHE.select(bothConfirmed, TFHE.asEuint64(0), d.amount);

        // Grant ACL to respective parties
        TFHE.allow(toSeller, d.seller);
        TFHE.allow(toBuyer,  d.buyer);

        d.released = true;
        // In a real contract: transfer tokens via the token contract here
    }
}

Delegate View Access

Sometimes a third party (an auditor, a protocol) needs to view an encrypted value, but not compute on it. You can grant read-only ACL access — they can call balanceOf and re-encrypt, but cannot use the handle in arithmetic.

Delegate View Implementation

Solidity
contracts/ConfidentialERC20.sol (delegate view)
// Mapping: owner => delegated viewer => approved
mapping(address => mapping(address => bool)) public viewDelegates;

function grantViewAccess(address viewer) external {
    viewDelegates[msg.sender][viewer] = true;
    // Grant persistent ACL so viewer can re-encrypt this balance
    TFHE.allow(_balances[msg.sender], viewer);
    emit ViewAccessGranted(msg.sender, viewer);
}

function revokeViewAccess(address viewer) external {
    viewDelegates[msg.sender][viewer] = false;
    // Note: ACL.allow() is NOT reversible — once granted, you cannot un-grant.
    // The viewer retains ACL access but the application layer records the revocation.
    // For true revocation, migrate to a new handle (e.g., re-mint or re-store).
    emit ViewAccessRevoked(msg.sender, viewer);
}

function balanceOf(
    address owner,
    bytes32 publicKey,
    bytes calldata signature
) external view returns (bytes memory) {
    // Allow owner OR a view delegate to call this function
    require(
        msg.sender == owner || viewDelegates[owner][msg.sender],
        "Not authorized to view balance"
    );
    return TFHE.reencrypt(_balances[owner], publicKey, 0);
}
🚫
ACL Grants Are Irrevocable
TFHE.allow(handle, addr) writes to the on-chain ACL contract and cannot be undone. If you need true revocation, the standard pattern is to replace the handle: store the value in a new ciphertext and grant access to the new handle only to the intended parties. The old handle remains accessible to previous grantees.

Common Cross-Contract Pitfalls

✘ Bug — Forgot ACL before cross-call
// Contract A passes handle to Contract B
// but never called allowTransient or allow
function forward(euint64 amt) external {
    // B cannot compute on amt — ACL rejects
    contractB.process(amt); // ← WILL FAIL
}
✓ Fix — Grant permission before cross-call
// Grant transient permission to B first
function forward(euint64 amt) external {
    TFHE.allowTransient(amt, address(contractB));
    contractB.process(amt); // ← Works!
}
✘ Bug — Transient for multi-tx access
// Escrow uses transient — future txs will fail
TFHE.allowTransient(amount, address(escrow));
escrow.deposit(amount);

// Later transaction...
escrow.release(); // ← FAILS: no ACL access
✓ Fix — Persistent allow for escrow
// Escrow needs multi-tx access: use allow()
TFHE.allow(amount, address(escrow));
TFHE.allowTransient(amount, address(escrow));
escrow.deposit(amount);

// Later transaction...
escrow.release(); // ← Works!

BCall TFHE.allowTransient(handle, address(contractB)) before the cross-contract call

DRegister Contract B in the ACL admin contract
Correct — B. Handles are public identifiers, but operating on the ciphertext requires ACL permission. allowTransient grants permission scoped to the current transaction — sufficient for same-tx composability.
QUESTION 02 / 06
An escrow contract stores a deposit in one transaction and needs to release it in a later transaction. Which ACL call should the depositor use?
ATFHE.allowTransient(amount, address(escrow))
BNo ACL call needed — escrow owns the handle after transfer
CTFHE.allowForDecryption(amount)
DTFHE.allow(amount, address(escrow))
Correct — D. allow writes a persistent ACL entry. The escrow needs to access the handle in its future release() transaction. allowTransient would expire at the end of the deposit transaction and the release would fail.
QUESTION 03 / 06
You call TFHE.allow(handle, viewer) to grant a viewer access, then later want to revoke it. What is the correct approach?
ACall TFHE.revoke(handle, viewer)
BCall TFHE.allow(handle, address(0)) to override
CACL grants are irrevocable — store the value in a new ciphertext and grant access to the new handle only to authorized parties
DDelete the ACL mapping entry in the ACL contract directly
Correct — C. TFHE.allow is a one-way operation. There is no revoke function. The standard pattern for revocation is to "re-mint" the value: store it in a new ciphertext handle and grant access to that new handle only to the parties that should retain access.
QUESTION 04 / 06
In the oblivious escrow release pattern, why must you use TFHE.select(bothConfirmed, amount, 0) instead of if (bothConfirmed) { transfer(amount) }?
AbothConfirmed is an ebool — Solidity cannot branch on encrypted values, so you must compute both outcomes and select between them obliviously
BTFHE.select is cheaper in gas
CThe if-statement would revert the transaction if the condition is false
DThe Gateway requires all transfers to use TFHE.select
Correct — A. An ebool is a ciphertext — its value is unknown at EVM execution time. Solidity's if requires a plaintext boolean. You must use TFHE.select to produce both branches as ciphertexts and select between them homomorphically.
QUESTION 05 / 06
What is a handle in FHEVM and is it safe to emit in events?
AA handle contains the encrypted ciphertext — emitting it reveals the data
BA handle is a uint256 identifier for a ciphertext stored in the coprocessor — it is safe to emit publicly, as it reveals nothing about the underlying value
CA handle is a hash of the user's address and value — it could leak information
DHandles must never be shared — doing so grants compute access to anyone
Correct — B. A handle is simply a deterministic identifier (like an index). The ciphertext itself lives in the off-chain coprocessor. Anyone can see a handle in an event, but without ACL permission they cannot decrypt or compute on the underlying ciphertext.
QUESTION 06 / 06
Contract A calls Contract B which calls Contract C, all in the same transaction. A owns handle h. For C to compute on h, what must happen?
AA must call allowTransient(h, B) only — B's permission automatically propagates to C
BNothing — all contracts in the same call stack share ACL access
CC must be registered as a trusted contract in the ACL admin
DEither A must call allowTransient(h, C), or B must call allowTransient(h, C) before calling C — transient permissions do not automatically propagate through call chains
Correct — D. ACL permissions are explicit and do not auto-propagate. Each contract in the chain needs its own grant. A can pre-grant C directly, or B can grant C when it receives the handle. The important thing is that the grant happens before the computation attempt.
