The DeFi Privacy Problem

Standard DeFi protocols publish every position in real-time. This creates three categories of harm:

FHEVM Confidential DeFi Architecture
All three protocols below follow the same pattern: encrypted state (euint64 balances/amounts), FHE arithmetic for invariant maintenance, FHE comparisons for condition checks, and Gateway decryption only for aggregate outputs that must be public (price oracles, global stats). Individual positions stay encrypted permanently.

Pattern 1 — Dark Pool AMM

A dark pool AMM maintains an x·y=k invariant over encrypted reserves. Traders submit encrypted swap amounts; the pool computes the output and updates reserves — all in FHE. The spot price is revealed only by the owner via a Gateway callback, acting as a price oracle.

Pool Architecture

euint64 — encrypted token A reserve. Never publicly readable.
💰
Reserve Y
euint64 — encrypted token B reserve. k = X·Y maintained in FHE.

Gateway decrypts reserves on request. Reveals price, not individual trades.

addLiquidity() — Encrypted Deposit

Soliditycontracts/DarkPoolAMM.sol — addLiquidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;
import "@fhevm/solidity/lib/FHE.sol";
import "@fhevm/solidity/config/ZamaConfig.sol";
import "@fhevm/solidity/gateway/GatewayCaller.sol";

contract DarkPoolAMM is ZamaEthereumConfig, GatewayCaller {

    euint64 private reserveX;   // encrypted reserve of token A
    euint64 private reserveY;   // encrypted reserve of token B

    // LP shares — plaintext; liquidity amounts are encrypted
    mapping(address => uint64) public lpShares;
    uint64 public totalShares;

    address public immutable owner;

    event LiquidityAdded(address indexed provider);
    event SwapExecuted(address indexed trader);
    event PriceRevealed(uint64 resX, uint64 resY);

    constructor() { owner = msg.sender; }

    /**
     * @notice Add liquidity with encrypted amounts.
     * amountX and amountY must maintain the existing price ratio — 
     * enforced off-chain by the LP. The contract trusts the amounts
     * are proportional (a separate invariant check can be added).
     */
    function addLiquidity(
        externalEuint64 calldata encX,
        bytes           calldata proofX,
        externalEuint64 calldata encY,
        bytes           calldata proofY,
        uint64          shares    // plaintext share amount requested
    ) external {
        euint64 amountX = FHE.fromExternal(encX, proofX);
        euint64 amountY = FHE.fromExternal(encY, proofY);

        // Initialisation: first liquidity provider sets the price
        if (totalShares == 0) {
            reserveX = amountX;
            reserveY = amountY;
        } else {
            // Accumulate reserves — price ratio maintained by LP
            reserveX = FHE.add(reserveX, amountX);
            reserveY = FHE.add(reserveY, amountY);
        }

        FHE.allowThis(reserveX); FHE.allowThis(reserveY);

        lpShares[msg.sender] += shares;
        totalShares          += shares;
        emit LiquidityAdded(msg.sender);
    }
}

swap() — The Dark Trade

SolidityDarkPoolAMM.sol — swap
/**
 * @notice Swap token X for token Y with encrypted input amount.
 * Uses the constant-product formula: amountOut = (reserveY * amountIn) / (reserveX + amountIn)
 * IMPORTANT: Division is not a native FHE operation — see note below.
 *
 * For production: use an approximation or fixed-point integer arithmetic.
 * This example uses a simplified fee-less integer approximation.
 */
function swapXforY(
    externalEuint64 calldata encAmountIn,
    bytes           calldata proof
) external {
    euint64 amountIn = FHE.fromExternal(encAmountIn, proof);

    // Step 1: Compute numerator = reserveY * amountIn (euint128 to avoid overflow)
    euint128 numerator = FHE.mul(
        FHE.asEuint128(reserveY),
        FHE.asEuint128(amountIn)
    );

    // Step 2: Compute denominator = reserveX + amountIn
    euint64 denominator = FHE.add(reserveX, amountIn);

    // Step 3: Integer division approximation
    // FHE.div() is O(N²) cost — use only when necessary
    // For production use pre-committed price bands or TWAP oracles
    euint64 amountOut = FHE.asEuint64(
        FHE.div(numerator, FHE.asEuint128(denominator))
    );

    // Step 4: Update reserves
    reserveX = FHE.add(reserveX, amountIn);
    reserveY = FHE.sub(reserveY, amountOut);

    FHE.allowThis(reserveX);
    FHE.allowThis(reserveY);

    // Step 5: Credit output to trader's encrypted balance
    // (requires an encrypted token contract integration)
    _creditTrader(msg.sender, amountOut);

    emit SwapExecuted(msg.sender);
}

function _creditTrader(address trader, euint64 amount) internal {
    // Grant trader access to their output amount handle
    FHE.allow(amount, trader);
    // In a real system: call the confidential token contract to mint/transfer
}
⚠
FHE Division — The Expensive Operation
FHE.div() is O(N²) in circuit complexity — roughly 64× the cost of FHE.add() for 64-bit operands. For a production AMM, consider these alternatives:

• Pre-committed price bands: Accept trades at the last published price ± a tolerance band. Price updated via Gateway callback every N blocks.
• TWAP oracle: Reveal aggregate price statistics (not individual trade prices) periodically.
• Fixed-ratio pools: StableSwap-style pools where the ratio is close to 1:1 — cheaper arithmetic.

Price Oracle via Gateway

SolidityDarkPoolAMM.sol — price oracle
/// @notice Owner can reveal current reserves to publish a price.
/// Individual trades are never revealed — only aggregate pool state.
function requestPriceReveal() external {
    require(msg.sender == owner, "Not owner");

    FHE.makePubliclyDecryptable(reserveX);
    FHE.makePubliclyDecryptable(reserveY);

    euint64[] memory handles = new euint64[](2);
    handles[0] = reserveX;
    handles[1] = reserveY;

    Gateway.requestDecryption(
        handles, this.priceCallback.selector,
        0, block.timestamp + 1 hours, false
    );
}

    uint256, uint64 resX, uint64 resY

Pattern 2 — Private Lending Protocol

A Compound-style lending protocol where collateral ratios and borrow positions are encrypted. Liquidation is triggered only when a health factor falls below threshold — computed entirely in FHE without revealing the actual amounts.

Encrypted Collateral & Borrow Positions

Soliditycontracts/PrivateLending.sol — storage & deposit
contract PrivateLending is ZamaEthereumConfig, GatewayCaller {

    // Encrypted positions per user
    mapping(address => euint64) private collateral;  // deposited collateral
    mapping(address => euint64) private borrowed;    // outstanding debt
    mapping(address => euint64) private interest;    // accrued interest

    // Plaintext: liquidation threshold factor (e.g. 150 = 150% overcollat)
    uint64 public constant LTV_FACTOR = 150;  // borrow up to 66% of collateral
    uint64 public constant LIQ_THRESHOLD = 120; // liquidate below 120%

    address public immutable owner;
    mapping(uint256 => address) private liquidationTarget; // reqId → user

    event Deposited(address indexed user);
    event Borrowed(address indexed user);
    event LiquidationRequested(address indexed user, uint256 reqId);
    event Liquidated(address indexed user, uint64 seized);

    constructor() { owner = msg.sender; }

    /// @notice Deposit encrypted collateral
    function deposit(
        externalEuint64 calldata enc, bytes calldata proof
    ) external {
        euint64 amount = FHE.fromExternal(enc, proof);

        if (euint64.unwrap(collateral[msg.sender]) == 0) {
            collateral[msg.sender] = amount;
        } else {
            collateral[msg.sender] = FHE.add(collateral[msg.sender], amount);
        }

        FHE.allowThis(collateral[msg.sender]);
        FHE.allow(collateral[msg.sender], msg.sender);
        FHE.allow(collateral[msg.sender], owner);
        emit Deposited(msg.sender);
    }
}

Health Factor Check in FHE

The health factor (collateral × 100 / debt) must stay above the liquidation threshold. This comparison is done entirely in FHE — no one learns the actual amounts, only whether the account is healthy or not.

SolidityPrivateLending.sol — borrow & health check
/// @notice Borrow against encrypted collateral.
/// Borrow amount is validated: borrowed * LTV_FACTOR <= collateral * 100
function borrow(
    externalEuint64 calldata enc, bytes calldata proof
) external {
    euint64 amount = FHE.fromExternal(enc, proof);

    // Compute total debt if borrow succeeds
    euint64 totalDebt = FHE.add(borrowed[msg.sender], amount);

    // Health check: collateral * 100 >= totalDebt * LTV_FACTOR
    // i.e. collateral / totalDebt >= LTV_FACTOR / 100
    euint64 collateral100 = FHE.mul(collateral[msg.sender], FHE.asEuint64(100));
    euint64 debtLTV       = FHE.mul(totalDebt, FHE.asEuint64(LTV_FACTOR));
    ebool   healthy       = FHE.gte(collateral100, debtLTV);

    // Only update borrowed if healthy — cap at current if not
    // (silent cap pattern: no revert to preserve privacy)
    borrowed[msg.sender] = FHE.select(healthy, totalDebt, borrowed[msg.sender]);

    FHE.allowThis(borrowed[msg.sender]);
    FHE.allow(borrowed[msg.sender], msg.sender);
    FHE.allow(borrowed[msg.sender], owner);
    emit Borrowed(msg.sender);
}

/// @notice Returns an encrypted bool: true = healthy, false = liquidatable.
/// Only the account owner and protocol owner can check their own health.
function isHealthy(address user) external view returns (ebool) {
    require(
        msg.sender == user || msg.sender == owner,
        "Not authorized"
    );
    euint64 collateral100 = FHE.mul(collateral[user], FHE.asEuint64(100));
    euint64 debtThreshold = FHE.mul(borrowed[user], FHE.asEuint64(LIQ_THRESHOLD));
    ebool   result        = FHE.gte(collateral100, debtThreshold);
    FHE.allow(result, msg.sender);
    return result;
}

Liquidation — Revealing Only What's Needed

SolidityPrivateLending.sol — liquidation
/**
 * @notice Request liquidation check for a user.
 * Owner calls this on any account. Gateway decrypts the health boolean.
 * If unhealthy, the callback seizes collateral.
 *
 * PRIVACY NOTE: The fact that liquidation was *requested* is visible.
 * The collateral amount is only revealed in the Liquidated event.
 */
function requestLiquidationCheck(address user) external {
    require(msg.sender == owner, "Only protocol owner");

    euint64 collateral100 = FHE.mul(collateral[user], FHE.asEuint64(100));
    euint64 debtThreshold = FHE.mul(borrowed[user], FHE.asEuint64(LIQ_THRESHOLD));
    ebool   isUnhealthy   = FHE.lt(collateral100, debtThreshold);

    FHE.makePubliclyDecryptable(isUnhealthy);
    ebool[] memory h = new ebool[](1);
    h[0] = isUnhealthy;

    uint256 reqId = Gateway.requestDecryption(
        h, this.liquidationCallback.selector,
        0, block.timestamp + 30 minutes, false
    );
    liquidationTarget[reqId] = user;
    emit LiquidationRequested(user, reqId);
}

function liquidationCallback(
    uint256 requestId, bool isUnhealthy
) external onlyGateway {
    if (!isUnhealthy) return; // account is healthy, no action needed

    address user = liquidationTarget[requestId];

    // Seize all collateral and zero out the debt
    euint64 seized  = collateral[user];
    FHE.makePubliclyDecryptable(seized); // liquidation amount becomes public

    collateral[user] = FHE.asEuint64(0);
    borrowed[user]   = FHE.asEuint64(0);
    FHE.allowThis(collateral[user]);
    FHE.allowThis(borrowed[user]);
    FHE.allow(collateral[user], user);
    FHE.allow(borrowed[user], user);

    // We'd need another Gateway call to get the plaintext seized amount
    // for the event. Here simplified for clarity.
    emit Liquidated(user, 0); // actual amount via separate callback
}

Pattern 3 — On-Chain Payroll

An employer stores encrypted salary schedules on-chain. Employees can only decrypt their own salary. The employer can pay out to all employees in a single batch transaction without any salary being visible to co-workers.

Encrypted Salary Registry

Soliditycontracts/PrivatePayroll.sol
contract PrivatePayroll is ZamaEthereumConfig {

    struct Employee {
        euint64  monthlySalary;    // encrypted — only employee can decrypt
        euint64  bonusPool;        // encrypted — only employee + HR can decrypt
        uint256  lastPaidAt;      // plaintext timestamp
        bool     active;          // plaintext active flag
    }

    mapping(address => Employee) private employees;
    address[] public employeeList;
    address public immutable employer;

    event EmployeeAdded(address indexed employee);
    event SalaryUpdated(address indexed employee);
    event PayrollRun(uint256 employeeCount, uint256 timestamp);

    constructor() { employer = msg.sender; }

    /**
     * @notice Register a new employee with encrypted salary.
     * Only HR (employer) can call. The employee address is public
     * (they're on the payroll), but the amount is private.
     */
    function addEmployee(
        address         employee,
        externalEuint64 calldata encSalary,
        bytes           calldata proof
    ) external {
        require(msg.sender == employer, "Only employer");
        require(!employees[employee].active, "Already registered");

        euint64 salary = FHE.fromExternal(encSalary, proof);

        employees[employee] = Employee({
            monthlySalary: salary,
            bonusPool:     FHE.asEuint64(0),
            lastPaidAt:    block.timestamp,
            active:        true
        });

        // Grant access: only employee and employer can decrypt salary
        FHE.allowThis(employees[employee].monthlySalary);
        FHE.allow(employees[employee].monthlySalary, employee);
        FHE.allow(employees[employee].monthlySalary, employer);

        FHE.allowThis(employees[employee].bonusPool);
        FHE.allow(employees[employee].bonusPool, employee);
        FHE.allow(employees[employee].bonusPool, employer);

        employeeList.push(employee);
        emit EmployeeAdded(employee);
    }
}

Batch Payroll Disbursement

SolidityPrivatePayroll.sol — runPayroll & viewSalary
/**
 * @notice Run monthly payroll: transfer salary to each employee's
 * encrypted balance in the confidential token contract.
 *
 * Gas note: O(N) FHE.allowTransient() + N token.transfer() calls.
 * For large payrolls (>50 employees), batch via off-chain merkle proof.
 */
function runPayroll(address tokenContract) external {
    require(msg.sender == employer, "Only employer");
    require(
        block.timestamp >= _lastPayrollRun + 28 days,
        "Too soon"
    );

    IConfidentialToken token = IConfidentialToken(tokenContract);

    for (uint256 i = 0; i < employeeList.length; i++) {
        address  emp = employeeList[i];
        Employee storage e = employees[emp];
        if (!e.active) continue;

        // Allow token contract to read the salary handle for this tx
        FHE.allowTransient(e.monthlySalary, tokenContract);

        // Token contract transfers the encrypted salary amount to employee
        token.transferEncrypted(emp, e.monthlySalary);

        e.lastPaidAt = block.timestamp;
    }

    _lastPayrollRun = block.timestamp;
    emit PayrollRun(employeeList.length, block.timestamp);
}

/// @notice Employee reads their own encrypted salary
function viewSalary() external view returns (euint64) {
    require(employees[msg.sender].active, "Not an employee");
    require(
        FHE.isSenderAllowed(employees[msg.sender].monthlySalary),
        "Not authorized"
    );
    return employees[msg.sender].monthlySalary;
}

/// @notice Update an employee's salary (employer only)
function updateSalary(
    address         employee,
    externalEuint64 calldata encNewSalary,
    bytes           calldata proof
) external {
    require(msg.sender == employer, "Only employer");
    euint64 newSalary = FHE.fromExternal(encNewSalary, proof);
    employees[employee].monthlySalary = newSalary;
    FHE.allowThis(newSalary);
    FHE.allow(newSalary, employee);
    FHE.allow(newSalary, employer);
    emit SalaryUpdated(employee);
}

Cross-Contract Composability Patterns

Passing Handles Between Contracts

When Contract A needs to pass an encrypted value to Contract B, two patterns exist depending on the interaction type:

PatternAPILifetimeWhen to Use
Persistent grantFHE.allow(handle, contractB)Permanent — survives across transactionsContract B stores or repeatedly accesses the handle (e.g., staking contract holding an LP position)
Transient grantFHE.allowTransient(handle, contractB)This transaction only — revoked afterContract B uses the handle only in this call (e.g., payroll disbursement calling a token contract)

Transient ACL in Practice

SolidityCross-contract FHE call pattern
// Contract A (caller): must grant transient access BEFORE calling Contract B
function compoundPosition(address yieldFarm) external {
    euint64 myBalance = _balances[msg.sender];

    // CRITICAL ORDER: allowTransient BEFORE the cross-contract call
    FHE.allowTransient(myBalance, yieldFarm);

    // Now Contract B (yieldFarm) can read myBalance in this transaction
    IYieldFarm(yieldFarm).depositEncrypted(msg.sender, myBalance);

    // After this call returns, the transient grant is automatically revoked
    // yieldFarm cannot use myBalance in any future transaction
}

// Contract B (callee): receives and uses the handle in the same transaction
function depositEncrypted(address user, euint64 amount) external {
    // This call succeeds because Contract A granted transient access
    euint64 newDeposit = FHE.add(_deposits[user], amount);
    _deposits[user] = newDeposit;

    // Must grant this contract persistent access to the NEW handle
    FHE.allowThis(newDeposit);
    FHE.allow(newDeposit, user);
}

// COMMON BUG — calling Contract B WITHOUT allowTransient first:
function buggyVersion(address yieldFarm) external {
    euint64 myBalance = _balances[msg.sender];
    // ❌ Missing: FHE.allowTransient(myBalance, yieldFarm);
    IYieldFarm(yieldFarm).depositEncrypted(msg.sender, myBalance);
    // ↑ REVERTS: "ACL: sender is not allowed" inside depositEncrypted()
}

QUESTION 01 / 08
Why is FHE.div() discouraged in AMM swap calculations, and what is the recommended alternative?
AFHE.div() doesn't exist — division is not supported in FHEVM
BFHE.div() always rounds down, introducing systematic pricing errors
CFHE.div() is O(N²) in circuit complexity — roughly 64× the cost of addition. Better alternatives include pre-committed price bands updated via Gateway, or TWAP oracles that reveal aggregate price without per-trade computation
DFHE.div() requires the denominator to be plaintext, which would leak reserve amounts
Correct — C. FHE integer division uses long-division circuit construction, resulting in O(N²) gate complexity for N-bit operands. For 64-bit numbers this is ~4096× the gates of addition. Production AMMs avoid it by publishing price oracles periodically or using pre-committed execution prices.
QUESTION 02 / 08
In the private lending protocol, why does borrow() use a silent cap (keeping current borrowed amount) rather than reverting when the health check fails?
AReverting would reveal that the requested amount exceeds the borrower's collateral capacity, leaking information about their actual collateral-to-debt ratio
BReverts are not supported inside FHE operations
CSilent cap is cheaper gas-wise than a revert
DThe health factor check is approximate, so reverting could incorrectly block valid borrows
Correct — A. If the contract reverted with "undercollateralized," the caller would know their debt-to-collateral ratio is above the LTV factor. This leaks private financial information. The silent cap preserves privacy: the transaction succeeds but the state update is a no-op — the caller can only tell their borrow didn't succeed by checking their encrypted balance later.
QUESTION 03 / 08
What must be called before a cross-contract call when passing an encrypted handle from Contract A to Contract B?
AFHE.allow(handle, contractB) — persistent grant
BFHE.allowThis(handle) — re-grant to this contract
CNo grant needed — handles are accessible to any contract that receives them as arguments
DFHE.allowTransient(handle, contractB) if B only needs it for this transaction, or FHE.allow(handle, contractB) if B needs persistent access
Correct — D. The ACL must be updated before Contract B can use the handle. allowTransient() is preferred when B only uses the handle within this call (cheaper, auto-revokes). allow() is needed when B stores and reuses the handle across transactions. Forgetting this is the most common cross-contract FHEVM bug.
QUESTION 04 / 08
In the dark pool AMM, what information does the PriceRevealed event leak?
ANothing — the event is also encrypted
BThe aggregate pool reserves (resX, resY) at the moment of the oracle call — enough to compute the current spot price, but no individual trade amounts or trader identities
CThe last trade amount and the direction of the trade
DThe total volume traded since pool creation
Correct — B. PriceRevealed(resX, resY) reveals the current pool reserves — which implies the current spot price (resY/resX). It does NOT reveal who traded, how much they traded, or at what price individual trades executed. This is an intentional design: price discovery requires some revelation, but trading privacy is preserved.
QUESTION 05 / 08
In the payroll contract, why is the employee list (employeeList) kept public while salaries are encrypted?
AEmployee addresses must be public for the payroll to function on-chain
BIt is an oversight — ideally all employment data should be encrypted
CDeliberate design: whether someone works at a company is typically not sensitive (publicly visible employment), while compensation is sensitive. This also allows external verification that payroll was run for all employees
DEncrypted address arrays are not supported by FHEVM
Correct — C. Employment itself (name on the company's payroll) is typically not confidential — it appears on LinkedIn, company websites, etc. Compensation is the sensitive data. This design separates these concerns: transparent accountability (everyone can verify payroll ran for all employees) with private amounts (only employer and employee know the figure).
QUESTION 06 / 08
What is the difference between FHE.allowTransient() and FHE.allow() in terms of grant lifetime?
AallowTransient() grants access for the current transaction only and is automatically revoked after; allow() creates a permanent ACL entry that persists across all future transactions
BallowTransient() grants access for 24 hours; allow() is permanent
CThey are identical — "transient" is just a naming convention
DallowTransient() is cheaper in gas; allow() is permanent and expensive
Correct — A. allowTransient() uses transient storage (EIP-1153) which is cleared at the end of each transaction. Perfect for single-transaction cross-contract calls. allow() writes to persistent storage — the grant remains forever (until explicitly revoked). Use allowTransient() by default when the recipient only needs one-time access within the current call.
QUESTION 07 / 08
In the lending protocol, the liquidation health check multiplies collateral * 100 and borrowed * LIQ_THRESHOLD. Why multiply rather than divide?
AFHE.div() is not available for euint64 types
BTo avoid integer overflow in the comparison
CThe Solidity compiler requires integer comparisons to use multiplication
DCross-multiplying avoids division: col/debt >= threshold/100 is equivalent to col*100 >= debt*threshold. This uses only FHE.mul() (much cheaper than FHE.div()) while achieving the same comparison result
Correct — D. This is the cross-multiplication trick: col/debt >= T/100 ↔ col*100 >= debt*T. No division needed — both sides are multiplied out. FHE.mul() is O(N log N) while FHE.div() is O(N²), so this saves significant gas. The only risk is overflow: col*100 must fit in euint64 (max ~1.8×10¹⁹), which means max collateral is ~1.8×10¹⁷ units — fine for 6-decimal tokens.
QUESTION 08 / 08
What metadata is still leaked even in a fully confidential on-chain payroll system?
ANothing — all payroll data is fully private with FHEVM
BThe list of employee wallet addresses, the dates payroll was run, the number of employees, and the gas cost of the payroll transaction (which correlates with employee count)
COnly the total payroll cost (sum of all salaries) is leaked
DThe salary range (min and max) is leaked through gas differential analysis
Correct — B. FHEVM hides amounts but not metadata. Anyone watching the blockchain sees: which addresses are on the payroll (employeeList is public), when payroll runs (timestamps in PayrollRun events), how many employees were paid (event parameter), and the gas cost of the transaction (which scales with employee count). For maximum privacy, use pseudonymous wallet addresses and run payroll through a relayer.
