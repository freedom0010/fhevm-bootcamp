Full Deployment Script

TypeScript
deploy/01_deploy_token.ts
import { HardhatRuntimeEnvironment } from 'hardhat/types'
import { DeployFunction } from 'hardhat-deploy/types'
import { network } from 'hardhat'

const func: DeployFunction = async (hre: HardhatRuntimeEnvironment) => {
  const { deployments, getNamedAccounts, ethers } = hre
  const { deploy, log } = deployments
  const { deployer } = await getNamedAccounts()

  log(`\n── Deploying ConfidentialERC20 on ${network.name} ──`)
  log(`   Deployer: ${deployer}`)

  // Check deployer balance before proceeding
  const balance = await ethers.provider.getBalance(deployer)
  if (balance < ethers.parseEther('0.05')) {
    throw new Error(`Insufficient balance: ${ethers.formatEther(balance)} ZAMA. Need at least 0.05.`)
  }

  const result = await deploy('ConfidentialERC20', {
    from: deployer,
    args: [
      'PrivateToken',   // name
      'PRIV',            // symbol
    ],
    log: true,
    waitConfirmations: network.name === 'hardhat' ? 1 : 3,
  })

  log(`\n✓ ConfidentialERC20 deployed at: ${result.address}`)
  log(`  tx: ${result.transactionHash}`)
  log(`  gas used: ${result.receipt?.gasUsed}`)

  // Write deployment info for frontend use
  const fs = await import('fs')
  fs.writeFileSync(
    './frontend/src/lib/deployment.json',
    JSON.stringify({
      network:  network.name,
      chainId:  network.config.chainId,
      address:  result.address,
      deployedAt: new Date().toISOString(),
    }, null, 2)
  )
}

func.tags = ['ConfidentialERC20']
export default func

Never Commit Private Keys
Add .env to .gitignore immediately. For mainnet deployments, use a hardware wallet (Ledger/Trezor) via @nomicfoundation/hardhat-ledger or an encrypted keystore (npx hardhat keystore) — never a raw private key in any file that could be committed or logged.

CI Secrets Setup (GitHub)

In your GitHub repository: Settings → Secrets and variables → Actions → New repository secret. Add these secrets (never put them in workflow YAML files directly):

  • DEPLOYER_PRIVATE_KEY — devnet-only deployer key (use a dedicated wallet with minimal funds)
  • DEVNET_RPC_URL — the RPC endpoint
  • CMC_API_KEY — optional, for gas USD pricing in reports

CI/CD Pipeline

GitHub Actions Workflow

yaml
.github/workflows/ci.yml
name: FHEVM CI/CD

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  # ── Stage 1: Fast checks ─────────────────────────
  lint-and-compile:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - name: Lint (Solhint)
        run: npx solhint 'contracts/**/*.sol'
      - name: Compile
        run: npx hardhat compile

  # ── Stage 2: Unit tests (mock mode, fast) ────────
  test-mock:
    needs: lint-and-compile
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - name: Run tests (mock FHE)
        run: npx hardhat test --network hardhat
      - name: Gas report
        run: REPORT_GAS=true npx hardhat test --network hardhat
        env:
          CMC_API_KEY: ${{ secrets.CMC_API_KEY }}
      - name: Upload gas report
        uses: actions/upload-artifact@v4
        with:
          name: gas-report
          path: gas-report.txt

  # ── Stage 3: Slither static analysis ────────────
  slither:
    needs: lint-and-compile
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      - run: pip install slither-analyzer
      - run: npm ci && npx hardhat compile
      - name: Run Slither
        run: slither contracts/ --exclude-dependencies
        continue-on-error: false

  # ── Stage 4: Devnet integration tests ────────────
  # Only runs on push to main (not on every PR)
  test-devnet:
    needs: [test-mock, slither]
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    environment: devnet
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - name: Run integration tests on devnet
        run: npx hardhat test --network devnet
        env:
          DEVNET_RPC_URL:       ${{ secrets.DEVNET_RPC_URL }}
          DEPLOYER_PRIVATE_KEY: ${{ secrets.DEPLOYER_PRIVATE_KEY }}

  # ── Stage 5: Deploy (only on tagged release) ─────
  deploy:
    needs: test-devnet
    runs-on: ubuntu-latest
    if: startsWith(github.ref, 'refs/tags/v')
    environment: devnet
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - name: Deploy to devnet
        run: npx hardhat deploy --network devnet
        env:
          DEVNET_RPC_URL:       ${{ secrets.DEVNET_RPC_URL }}
          DEPLOYER_PRIVATE_KEY: ${{ secrets.DEPLOYER_PRIVATE_KEY }}
      - name: Verify contracts
        run: npx hardhat etherscan-verify --network devnet
        env:
          DEVNET_RPC_URL: ${{ secrets.DEVNET_RPC_URL }}

Pipeline Stage Summary

1

Lint + Compile (~1 min)

Solhint checks code style; hardhat compile validates Solidity. Runs on every push and PR.

2

Mock Tests + Gas Report (~3 min)

Full test suite against mock FHE — fast, no RPC needed. Uploads gas report as artifact for review.

3

Slither Analysis (~2 min)

Static analysis for common vulnerabilities. Fails the pipeline on high-severity findings.

4

Devnet Integration (~8 min)

Tests against real FHEVM network — Gateway callbacks, real KMS latency. Only runs on main branch.

5

Deploy + Verify (on tag)

Triggered by git tag v1.0.0 && git push --tags. Deploys and verifies source on the explorer.

Monitoring & Observability

After deployment, you need visibility into: Gateway callback latency, failed transactions, unusual usage patterns (e.g., a flood of bids suggesting a spam attack), and contract state changes.

Event Indexer with viem

TypeScript
monitor/indexer.ts
import { createPublicClient, http, parseAbiItem } from 'viem'

const client = createPublicClient({
  transport: http('https://devnet.zama.ai'),
})

const CONTRACT = '0xYOUR_CONTRACT_ADDRESS' as const

// Watch BidPlaced events in real time
client.watchContractEvent({
  address: CONTRACT,
  abi: [parseAbiItem('event BidPlaced(address indexed bidder)')],
  eventName: 'BidPlaced',
  onLogs: (logs) => {
    logs.forEach(log => {
      console.log(`[${new Date().toISOString()}] Bid placed by ${log.args.bidder}`)
      // Send to your monitoring dashboard / Slack webhook
      sendAlert(`New bid from ${log.args.bidder}`)
    })
  },
})

// Track callback latency
const pendingRequests = new Map<bigint, number>()

client.watchContractEvent({
  address: CONTRACT,
  abi: [parseAbiItem('event AuctionEnded(uint256 indexed requestId)')],
  eventName: 'AuctionEnded',
  onLogs: (logs) => {
    logs.forEach(log => pendingRequests.set(log.args.requestId!, Date.now()))
  },
})

client.watchContractEvent({
  address: CONTRACT,
  abi: [parseAbiItem('event WinnerRevealed(address indexed winner, uint64 amount)')],
  eventName: 'WinnerRevealed',
  onLogs: (logs) => {
    logs.forEach(log => {
      const reqId = 0n  // correlate via requestId if tracked
      const latencyMs = Date.now() - (pendingRequests.get(reqId) ?? Date.now())
      console.log(`[KMS latency] ${latencyMs}ms — winner: ${log.args.winner}`)
    })
  },
})

async function sendAlert(msg: string) {
  await fetch(process.env.SLACK_WEBHOOK_URL!, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ text: `🔒 FHEVM Monitor: ${msg}` }),
  })
}

Upgradeability Considerations

FHEVM contracts can use the standard OpenZeppelin proxy upgrade pattern (TransparentUpgradeableProxy or UUPS). However, there are FHEVM-specific constraints to be aware of:

  • ACL handles are permanent — existing ciphertext handles survive an upgrade, but new logic versions must be compatible with the old ACL grants
  • Storage layout must be preserved — if you change where _balances is stored, existing encrypted values will be read as wrong handles
  • Gateway requestIds are external — outstanding decryption requests from the old implementation will callback to the proxy, which must still route them correctly after upgrade
  • Use OpenZeppelin's storage gap pattern — add uint256[50] private __gap; at the end of each upgradeable contract to reserve space for future variables
💡
When in Doubt — Don't Upgrade
FHEVM encrypted state is harder to migrate than plaintext state. For most production contracts, deploying a new version and migrating via a plaintext snapshot + re-encryption ceremony is safer than in-place upgrade logic. Reserve upgrade proxies for contracts with very active user state that makes migration impractical.

6 questions · deployment & CI/CD
QUESTION 01 / 06
Why should KMS, ACL, and Gateway contract addresses never be hardcoded in your Solidity contract?
AHardcoding wastes gas due to extra bytes in bytecode
BThe Solidity compiler rejects hardcoded addresses
CThese system contract addresses change between network versions — hardcoding breaks the contract on every network upgrade without redeployment
DThey must be kept private to prevent front-running
Correct — C. Zama's system contracts are upgraded and redeployed as the FHEVM evolves. A contract with hardcoded addresses would break silently after a network upgrade. Always read addresses from a configuration file or constructor argument and verify against the current documentation.
QUESTION 02 / 06
In the CI/CD pipeline, why do integration tests against the real devnet only run on pushes to main, not on every PR?
AGitHub Actions does not support devnet RPC connections on PR builds
BDevnet tests take ~8 minutes (real KMS latency), cost real tokens, and require production secrets — running them on every PR would be slow and wasteful. Mock tests catch 95% of bugs faster.
CPR branches cannot access environment secrets
DDevnet has a rate limit of one connection per repository
Correct — B. The tiered pipeline design runs fast mock tests on every PR (catching logic bugs in seconds) and reserves expensive devnet tests for code that's already been reviewed and is ready to merge. This balances developer velocity with thorough testing.
QUESTION 03 / 06
What is the correct way to trigger the deploy stage in the GitHub Actions pipeline shown today?
APush any commit to main
BOpen a pull request to main
CManually trigger via the Actions tab
DCreate and push a tag starting with v — for example git tag v1.0.0 && git push --tags
Correct — D. The pipeline uses if: startsWith(github.ref, 'refs/tags/v') to gate the deploy stage. This ensures deploys are intentional, versioned, and traceable — not triggered by every merge to main.
QUESTION 04 / 06
When upgrading a FHEVM contract using a proxy, what is the most critical constraint to maintain?
AThe storage layout must be preserved — changing where encrypted mappings are stored would cause existing handles to be read from wrong storage slots, corrupting all encrypted state
BAll ACL grants must be re-issued after every upgrade
CThe contract address must remain the same as the KMS address
DThe new implementation must re-encrypt all stored ciphertexts
Correct — A. FHEVM handles are uint256 values stored at specific storage slots. If you reorder state variables, the handle stored at slot N now refers to a different ciphertext. This silently corrupts all encrypted balances. Use OpenZeppelin's storage gap pattern to safely add variables in future upgrades.
QUESTION 05 / 06
What does the waitConfirmations: 3 parameter in the deployment script accomplish?
AIt retries the deployment transaction up to 3 times on failure
BIt sets the gas price to 3× the base fee
CIt waits for 3 blocks to be mined after deployment before proceeding — ensuring the deployment is deeply confirmed and the contract is safely indexed by the explorer before any subsequent setup transactions
DIt requests 3 validator signatures for the deployment transaction
Correct — C. On live networks, waitConfirmations adds safety margin. A single confirmation could be orphaned in a chain reorg. 3 confirmations ensures the deployment is stable before any subsequent transactions (like minting initial supply or setting permissions) that depend on the deployed address.
QUESTION 06 / 06
You want to monitor KMS callback latency in production. What is the correct approach using on-chain events?
APoll the Gateway contract's getPendingRequests() view function every second
BRecord the timestamp when AuctionEnded (requestDecryption) is emitted, then compute the delta when WinnerRevealed (callback) fires — the difference is the KMS round-trip latency
CSubscribe to the KMS contract's internal events directly
DUse block timestamps from the two transactions — subtract them in Solidity and emit the result
Correct — B. Record Date.now() off-chain when the request event fires, then subtract it from Date.now() when the callback event fires. This gives you wall-clock KMS latency with millisecond precision — more useful than block timestamps which have 12-second granularity.
