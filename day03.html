The FHE.sol Library

The @fhevm/solidity package contains everything you need. Three imports cover all cases:

ImportProvides
@fhevm/solidity/lib/FHE.solAll FHE ops: add, sub, mul, gt, eq, select, allow, fromExternal, asEuintX, …

The FHEVM Type System

euint vs externalEuint — Two Formats, One Value

🔑
Critical Distinction
euint32 — internal on-chain handle. A 32-byte pointer to a ciphertext on the coprocessor. Used for storage variables, return values, and intermediate results inside your contract.

externalEuint32 — the user-submitted input format from fhevmjs. Contains the raw ciphertext blob. Must be validated and converted via FHE.fromExternal() before any FHE operation. Cannot be stored directly.

fromExternal() — The Entry Gate

🔒
What fromExternal() Validates
FHE.fromExternal(encInput, proof) verifies a zero-knowledge proof that the ciphertext was encrypted specifically for:
• This contract address — prevents replay attacks to other contracts
• msg.sender — prevents stealing and replaying another user's input
• The exact ciphertext content — prevents tampering

If any of these don't match, the transaction reverts. This is why users must re-encrypt for every new call.

Transforming Plain Counter → Encrypted Counter

Side-by-Side: Every Change Explained

✗ Counter.sol (plaintext)
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Counter {
  uint32 private count;

  function add(
    uint32 amount
  ) external {
    count += amount;
  }

  function getCount()
    external view returns(uint32)
  {
    return count;
  }
}
✓ FHECounter.sol (encrypted)
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;
import "@fhevm/solidity/lib/FHE.sol";
import "@fhevm/solidity/config/ZamaConfig.sol";

contract FHECounter is ZamaEthereumConfig {
  euint32 private count;    // ← encrypted

  function add(
    externalEuint32 calldata enc,
    bytes calldata proof
  ) external {
    euint32 amt = FHE.fromExternal(enc,proof);
    count = FHE.add(count, amt);
    FHE.allowThis(count);
    FHE.allow(count, msg.sender);
  }

  function getCount()
    external view returns(euint32)
  {
    require(FHE.isSenderAllowed(count));
    return count;
  }
}

Every change has a reason: imports add FHE ops + network config; euint32 is the encrypted type; externalEuint32 + proof is the validated user input; fromExternal validates the ZK proof; allowThis + allow grant ACL permissions to the new handle.

The Complete FHECounter Contract

Constructor Pattern

Always initialize encrypted storage variables in the constructor — an uninitialized euint32 is the zero handle (all bytes zero), which has no ACL grants and will cause reverts if used without initialization.

Soliditycontracts/FHECounter.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@fhevm/solidity/lib/FHE.sol";
import "@fhevm/solidity/config/ZamaConfig.sol";

contract FHECounter is ZamaEthereumConfig {

    euint32 private count;        // encrypted handle stored on-chain
    address public immutable owner;
    uint32  public txCount;       // plaintext tx counter (public metadata)

    event Added(address indexed by);   // no amount — privacy
    event Reset(address indexed by);

    constructor() {
        owner = msg.sender;
        // MUST initialize: asEuint32(0) creates a proper handle for zero
        count = FHE.asEuint32(0);
        FHE.allowThis(count);          // contract can use it in future txs
        FHE.allow(count, msg.sender);   // deployer can decrypt initial value
    }

    /**
     * @notice Add an encrypted amount to the counter.
     * @param encAmount  User-encrypted value (from fhevmjs)
     * @param proof      ZK proof binding ciphertext to this contract + caller
     */
    function add(
        externalEuint32 calldata encAmount,
        bytes           calldata proof
    ) external {
        // Validate ZK proof and get an internal handle
        euint32 amount = FHE.fromExternal(encAmount, proof);

        // FHE addition — result is a brand-new handle
        count = FHE.add(count, amount);

        // ACL: grant permissions to the new handle
        FHE.allowThis(count);
        FHE.allow(count, msg.sender);
        FHE.allow(count, owner);

        txCount++;
        emit Added(msg.sender);
    }

    // Read the encrypted count (only authorized callers)
    function getCount() external view returns (euint32) {
        require(
            FHE.isSenderAllowed(count),
            "FHECounter: not authorized"
        );
        return count;
    }

    // Grant another address decryption access (owner only)
    function grantAccess(address viewer) external {
        require(msg.sender == owner, "Not owner");
        FHE.allow(count, viewer);
    }

    // Reset counter to zero (owner only)
    function reset() external {
        require(msg.sender == owner, "Not owner");
        count = FHE.asEuint32(0);
        FHE.allowThis(count);
        FHE.allow(count, owner);
        emit Reset(msg.sender);
    }
}

The FHE.select() Pattern — No if/else on Encrypted Values

⚠
Critical Rule — Never Branch on Encrypted Booleans
You cannot use if (encBool) — the EVM cannot evaluate an encrypted condition. Instead, always compute both branches and use FHE.select(condition, ifTrue, ifFalse) to pick the result. This is the single most important FHEVM programming pattern.
✗ WRONG — cannot branch on encrypted value
ebool isPositive = FHE.gt(balance, zero);
// ❌ COMPILE ERROR or LOGIC ERROR:
if (isPositive) {
    result = FHE.add(balance, amount);
} else {
    result = balance;
}
✓ CORRECT — use FHE.select()
ebool isPositive = FHE.gt(balance, zero);
// ✓ Compute both branches, pick with select:
euint64 added   = FHE.add(balance, amount);
euint64 kept    = balance;
result = FHE.select(isPositive, added, kept);
FHE.allowThis(result);
FHE.allow(result, msg.sender);

TypeScript Test Suite

FHEVM tests require the fhevmjs SDK to encrypt inputs client-side before sending them to the contract. The flow is: create instance → encrypt inputs → call contract → decrypt result.

Creating the FhevmInstance

TypeScripttest/helpers.ts
import { ethers } from "hardhat";
import { createFhevmInstance, FhevmInstance } from "fhevmjs";

let fhevmInstance: FhevmInstance;

export async function getFhevmInstance(): Promise<FhevmInstance> {
  if (fhevmInstance) return fhevmInstance;

  // Fetch network-specific FHE public key from the local node
  const provider = ethers.provider;
  fhevmInstance = await createFhevmInstance({
    chainId: (await provider.getNetwork()).chainId,
    networkUrl: provider._getConnection().url,
    gatewayUrl: "http://localhost:7077",  // local gateway
    aclAddress: "0x339EcE85B9E11a3A3AA557582784a15d7F82AAf2",
  });

  return fhevmInstance;
}

// Helper: encrypt a uint32 value for a specific contract + user
export async function encryptUint32(
  value: number,
  contractAddress: string,
  userAddress: string
) {
  const instance = await getFhevmInstance();
  const input = instance.createEncryptedInput(contractAddress, userAddress);
  input.add32(value);           // encrypt as euint32
  const encrypted = await input.encrypt();
  return {
    handles: encrypted.handles,   // the ciphertext
    inputProof: encrypted.inputProof  // ZK proof
  };
}

Full Test Suite

TypeScripttest/FHECounter.test.ts
import { ethers } from "hardhat";
import { expect } from "chai";
import { getFhevmInstance, encryptUint32 } from "./helpers";

describe("FHECounter", () => {
  let counter: any;
  let owner: any, alice: any;

  before(async () => {
    [owner, alice] = await ethers.getSigners();

    // Deploy the contract
    const Factory = await ethers.getContractFactory("FHECounter");
    counter = await Factory.deploy();
    await counter.waitForDeployment();
    console.log("  Contract deployed at:", await counter.getAddress());
  });

  it("adds an encrypted value and txCount increments", async () => {
    const addr = await counter.getAddress();

    // Encrypt 42 for owner calling this contract
    const { handles, inputProof } = await encryptUint32(
      42, addr, owner.address
    );

    await counter.connect(owner).add(handles[0], inputProof);

    const txCount = await counter.txCount();
    expect(txCount).to.equal(1n);
  });

  it("owner can retrieve and decrypt the count", async () => {
    const instance = await getFhevmInstance();
    const addr     = await counter.getAddress();

    // Get the encrypted handle from the contract
    const handle = await counter.connect(owner).getCount();

    // Re-encrypt under owner's keypair so they can decrypt locally
    const { publicKey, privateKey } = instance.generateKeypair();
    const eip712 = instance.createEIP712(publicKey, addr);
    const sig = await owner.signTypedData(
      eip712.domain, eip712.types, eip712.message
    );
    const reencrypted = await instance.reencrypt(
      handle, privateKey, publicKey, sig, addr, owner.address
    );
    const decrypted = instance.decrypt(addr, reencrypted);

    console.log("  Decrypted count:", decrypted);
    expect(decrypted).to.equal(42);
  });

  it("alice cannot read the count (no ACL grant)", async () => {
    await expect(
      counter.connect(alice).getCount()
    ).to.be.revertedWith("FHECounter: not authorized");
  });

  it("owner can grant alice access then alice reads", async () => {
    await counter.connect(owner).grantAccess(alice.address);
    // Now alice can call getCount without reverting
    const handle = await counter.connect(alice).getCount();
    expect(handle).to.not.equal("0x");
  });

  it("adds two values — count equals 42 + 10 = 52", async () => {
    const instance = await getFhevmInstance();
    const addr     = await counter.getAddress();

    // Add 10 more
    const { handles, inputProof } = await encryptUint32(10, addr, owner.address);
    await counter.connect(owner).add(handles[0], inputProof);

    // Decrypt and check
    const handle = await counter.connect(owner).getCount();
    const { publicKey, privateKey } = instance.generateKeypair();
    const eip712 = instance.createEIP712(publicKey, addr);
    const sig = await owner.signTypedData(eip712.domain, eip712.types, eip712.message);
    const reenc = await instance.reencrypt(handle, privateKey, publicKey, sig, addr, owner.address);
    expect(instance.decrypt(addr, reenc)).to.equal(52);
  });

  it("reset sets count to 0 (owner only)", async () => {
    await expect(
      counter.connect(alice).reset()
    ).to.be.revertedWith("Not owner");

    await counter.connect(owner).reset();
    expect(await counter.txCount()).to.equal(2n);
    // txCount doesn't reset — only the encrypted value does
  });
});

Re-encryption vs. Public Decryption

MethodHow It WorksWhen to Use
Re-encryptionKMS re-encrypts the value under the user's ephemeral public key; user decrypts locally. Plaintext never appears on-chain.User viewing their own private value (balance, score, etc.)
Public Decryption (Gateway callback)KMS decrypts and Gateway delivers plaintext to the contract. Plaintext appears in tx calldata.Revealing a result publicly (auction winner, game outcome)

Day 03 Quiz — Toolchain & First Contract
8 questions · hardhat-fhevm setup
QUESTION 01 / 08
What is the difference between euint32 and externalEuint32?
Aeuint32 is for public values; externalEuint32 is for private ones
Beuint32 stores 32 bits; externalEuint32 stores 64 bits
Ceuint32 is an internal on-chain handle; externalEuint32 is the raw ciphertext format submitted by users that must be validated via fromExternal() before use
DThey are identical — the names are interchangeable
Correct — C. euint32 is a 32-byte handle (a pointer) to a ciphertext stored on the coprocessor. externalEuint32 is the raw ciphertext blob submitted by the user's browser via fhevmjs. Before any FHE operation, externalEuint32 must be converted to euint32 via FHE.fromExternal(), which also validates the ZK proof binding the ciphertext to this specific contract and caller.
QUESTION 02 / 08
Why does FHE.fromExternal(enc, proof) require a ZK proof?
ATo compress the ciphertext to a smaller on-chain representation
BTo verify the ciphertext was encrypted specifically for this contract address and msg.sender — preventing replay attacks and input theft across contracts or callers
CTo check that the plaintext value is within the allowed range
DTo authorize the KMS to decrypt the input for verification
Correct — B. The ZK proof (inputProof) proves that the ciphertext was encrypted for this specific contract address AND this specific msg.sender. Without it, an attacker could take someone else's encrypted input (e.g., "I have 1000 tokens") and replay it in a different transaction or against a different contract.
QUESTION 03 / 08
You have ebool isGt = FHE.gt(a, b). How do you use this condition to produce different results?
Aif (isGt) { result = x; } else { result = y; }
Bresult = isGt ? x : y;
Cresult = FHE.ifElse(isGt, x, y);
DCompute both branches then: result = FHE.select(isGt, x, y);
Correct — D. You cannot branch on an encrypted boolean — the EVM cannot evaluate it. FHE.select() evaluates both branches and uses the encrypted condition to pick one, without ever revealing which branch was taken. This is the fundamental pattern for conditional logic in FHEVM contracts.
QUESTION 04 / 08
What happens if you declare euint32 private count but never call FHE.asEuint32(0) in the constructor?
AThe count is the zero handle (all bytes 0x00), which has no ACL grants — any FHE operation using it will revert on the ACL check
BIt automatically initializes to an encrypted 0 with full ACL grants
CThe Solidity compiler will reject uninitialized euint variables
DThe contract will compile and work, but with lower gas efficiency
Correct — A. An uninitialized euint32 defaults to bytes32(0) — the zero handle. This handle has no ACL grants and no corresponding ciphertext on the coprocessor. Any FHE.add(count, ...) will fail the ACL check. Always initialize encrypted storage with FHE.asEuintX(0) and call allowThis().
QUESTION 05 / 08
Which type would you choose to store an encrypted token balance that can reach up to 10¹⁸ (standard ERC-20 with 18 decimals)?
Aeuint32 — sufficient for most balances
Beuint128 — maximum safety for all amounts
Ceuint64 — max value ~1.8×10¹⁹ safely covers 10¹⁸, and uses 16× baseline gas vs euint128's 24×
Deuint256 — must match Solidity's uint256 for ERC-20 compatibility
Correct — C. euint64 has a max of ~1.8×10¹⁹, which safely covers 10¹⁸ (1 ETH in wei). It costs 16× baseline gas vs euint4's 1× baseline. euint128 would also work but wastes 50% more gas than necessary. euint256 is rarely needed and costs 2× euint128. Always use the smallest type that fits.
QUESTION 06 / 08
In the test suite, what is the purpose of the re-encryption step (instance.reencrypt())?
AIt re-encrypts the value for storage efficiency
BIt re-encrypts the ciphertext under the user's ephemeral public key, so the user can decrypt locally — the plaintext never appears on-chain
CIt re-encrypts the value under a new key to prevent replay attacks
DIt is a test-only helper that bypasses the KMS entirely
Correct — B. Re-encryption is the privacy-preserving way for a user to view their own data. The KMS re-encrypts the ciphertext under the user's ephemeral keypair (generated fresh for each view request). The user decrypts locally using their private key. The plaintext never appears in any transaction or on-chain state.
QUESTION 07 / 08
Why does the FHECounter emit event Added(address indexed by) but not the amount added?
AEvent parameters can only be of plaintext types — euint32 cannot be emitted
BEmitting the handle would expose the ciphertext to block explorers
CGas optimization — emitting amounts costs too much
DPrivacy design — emitting the encrypted amount as a handle would leak metadata about transaction patterns; only the caller address is revealed (which is already public on-chain)
Correct — D. While you technically could emit the handle, doing so reveals that a specific address added a specific (opaque) amount at a specific time. For privacy-sensitive contracts, even metadata leakage should be minimized. The event only records that an addition happened and by whom — the amount remains private.
QUESTION 08 / 08
After calling count = FHE.add(count, amount), which ACL calls are required at minimum to keep the contract functional?
AFHE.allowThis(count) — without this, the contract cannot use the new handle in any future transaction
BFHE.allow(count, msg.sender) — without this the caller cannot decrypt
CBoth allowThis and allow(msg.sender) are equally required
DNone — ACL grants are inherited from input handles automatically
Correct — A. The bare minimum for a contract that stores and reuses an encrypted value is FHE.allowThis(). Without it, the contract cannot access the new handle on any subsequent transaction, breaking all future operations. FHE.allow(count, msg.sender) is best practice (so the caller can decrypt) but if you omit it, the contract still functions — only the caller can't view their value. allowThis is the truly critical one.
