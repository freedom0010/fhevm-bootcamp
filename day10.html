Hardhat FHE Test Environment

Mock Mode vs. Real FHE Mode

The FHEVM Hardhat plugin provides two execution modes for tests. Understanding the difference is critical for test design:

FeatureMock Mode (HARDHAT_FHEVM_MOCK=true)Real FHE Mode (local node)
FHE operationsPlaintext arithmetic — no actual encryptionFull BFV/TFHE encryption on coprocessor
Test speed~10× faster — no cryptographic overheadNormal contract speed + ~2s coprocessor delay
Gateway callbacksImmediate — mock fires callback inline~2 second async delay
ZK proof validationSkipped — fromExternal() always succeedsFull proof verification
ACL enforcementEnforced — ACL checks still applyEnforced
Best forLogic bugs, ACL bugs, unit testsIntegration tests, proof validation, gas measurement
⚠
Always Test in Both Modes
Mock mode skips ZK proof verification — so a broken proof will pass in mock but fail in production. Your CI pipeline should run the full test suite in both modes. Use mock mode for fast iteration and real-FHE mode for pre-deployment validation.

The fhevm-test-helpers Library

Build this helper module once and import it in every test file. It standardizes the repetitive setup — instance creation, encryption, re-encryption, and decryption — so your test bodies stay focused on logic.

Instance Management

TypeScripttest/helpers/fhevm.ts
import { ethers } from "hardhat";
import { createFhevmInstance, FhevmInstance } from "fhevmjs";

// Singleton — one instance per test run (expensive to create)
let _instance: FhevmInstance | null = null;

export async function getInstance(): Promise<FhevmInstance> {
  if (_instance) return _instance;

  const provider = ethers.provider;
  const network  = await provider.getNetwork();

  _instance = await createFhevmInstance({
    chainId:    network.chainId,
    networkUrl: provider._getConnection().url,
    gatewayUrl: process.env.GATEWAY_URL || "http://localhost:7077",
    aclAddress: process.env.ACL_ADDRESS  || "0x339EcE85B9E11a3A3AA557582784a15d7F82AAf2",
  });

  return _instance;
}

// Reset between test suites if needed
export function resetInstance(): void { _instance = null; }

Encrypt Helpers — All Types

TypeScripttest/helpers/encrypt.ts
import { getInstance } from "./fhevm";

export interface EncryptedInput {
  handles:    Uint8Array[];
  inputProof: Uint8Array;
}

/**
 * Generic encrypted input helper.
 * contractAddress — the contract that will call fromExternal()
 * userAddress     — the msg.sender that will call the function
 */
async function encryptValue(
  value:           number | bigint | boolean,
  type:            "bool" | "8" | "16" | "32" | "64" | "128",
  contractAddress: string,
  userAddress:     string
): Promise<EncryptedInput> {
  const instance = await getInstance();
  const input    = instance.createEncryptedInput(contractAddress, userAddress);

  switch (type) {
    case "bool": input.addBool(value as boolean); break;
    case "8":    input.add8(Number(value));        break;
    case "16":   input.add16(Number(value));       break;
    case "32":   input.add32(Number(value));       break;
    case "64":   input.add64(BigInt(value));       break;
    case "128":  input.add128(BigInt(value));      break;
  }

  const encrypted = await input.encrypt();
  return { handles: encrypted.handles, inputProof: encrypted.inputProof };
}

// Typed convenience wrappers
export const encBool   = (v: boolean, c: string, u: string) => encryptValue(v, "bool", c, u);
export const encUint8  = (v: number,  c: string, u: string) => encryptValue(v, "8",    c, u);
export const encUint16 = (v: number,  c: string, u: string) => encryptValue(v, "16",   c, u);
export const encUint32 = (v: number,  c: string, u: string) => encryptValue(v, "32",   c, u);
export const encUint64 = (v: bigint,  c: string, u: string) => encryptValue(v, "64",   c, u);

Decrypt Helpers — Re-encryption Flow

TypeScripttest/helpers/decrypt.ts
import { ethers } from "hardhat";
import { getInstance } from "./fhevm";

/**
 * Full re-encryption + local decryption flow.
 * Returns the plaintext value as bigint.
 *
 * @param handle          The euint/ebool handle returned by the contract
 * @param contractAddress Address of the contract that owns the handle
 * @param signer          The authorized signer (must have ACL grant for handle)
 */
export async function decryptHandle(
  handle:          bigint,
  contractAddress: string,
  signer:          any
): Promise<bigint> {
  const instance = await getInstance();

  // Generate fresh ephemeral keypair for this decryption request
  const { publicKey, privateKey } = instance.generateKeypair();

  // Create EIP-712 typed data for the KMS re-encryption request
  const eip712  = instance.createEIP712(publicKey, contractAddress);
  const sig     = await signer.signTypedData(
    eip712.domain, eip712.types, eip712.message
  );

  // Request re-encryption from KMS (or mock in test mode)
  const reencrypted = await instance.reencrypt(
    handle,
    privateKey,
    publicKey,
    sig,
    contractAddress,
    signer.address
  );

  // Decrypt locally with our private key — plaintext never hits the network
  return instance.decrypt(contractAddress, reencrypted);
}

// Shortcut for boolean handles
export async function decryptBool(
  handle: bigint, contractAddress: string, signer: any
): Promise<boolean> {
  return (await decryptHandle(handle, contractAddress, signer)) !== 0n;
}

Common FHEVM Errors & Fixes

FHEVM contracts fail in predictable ways. This reference covers every error class you'll encounter, with the exact error message, root cause, and fix.

ACL Errors

🔒
Error Class 1 — ACL Not Authorized
Triggered when a contract or address tries to use a ciphertext handle it was never granted access to.
Error: VM Exception while processing transaction: reverted with reason string 'ACL: sender is not allowed' -- or -- 'FHEExecutor: ciphertext is not authorized for this operation'
ScenarioRoot CauseFix
Second transaction fails after first workedallowThis() missing after FHE op. New handle has zero grants.Add FHE.allowThis(newHandle) after every op that creates a new handle.
Cross-contract call failsCalling contract never received allowTransient() before being called.Add FHE.allowTransient(handle, contractB) before calling ContractB.
View function fails for authorized userFHE.allow(handle, user) was not called after the last write that created a new handle.After every storage write that updates an encrypted var, re-grant all viewers.
Constructor initializes fine; first call failsConstructor granted allowThis() on the initial handle, but the first transaction's new handle was never granted.Ensure every write path (not just constructor) calls allowThis().

Input Proof Errors

Error: VM Exception: reverted with reason string 'KMSVerifier: invalid proof' -- or -- 'FHE.fromExternal: ZK proof does not match contract + caller'
ScenarioRoot CauseFix
Proof works in one test, fails in anotherProof was generated for a different contractAddress or userAddress. ZK proof is bound to both.Always pass the exact contract address and caller address to createEncryptedInput(contractAddr, callerAddr).
Proof fails after contract redeploymentContract address changed. Old proof is bound to old address.Re-encrypt after every deployment. Never cache encrypted inputs across deployments.
Proxy contract fails even with correct addressesProof is bound to proxy address, but msg.sender context changes through delegatecall.Use the implementation address in createEncryptedInput(), or design proxy to preserve msg.sender context.

Gateway & Callback Errors

Error: Gateway callback never fired — requestDecryption() returned but callback was not called -- or -- Error: 'GatewayCaller: onlyGateway — sender is not the Gateway' -- or -- Error: 'FHE.makePubliclyDecryptable must be called before requestDecryption'
ScenarioRoot CauseFix
Callback never fires in productionmakePubliclyDecryptable() not called before Gateway.requestDecryption().Always call FHE.makePubliclyDecryptable(handle) for every handle being decrypted publicly.
Fake callback injection attack surfaceCallback lacks onlyGateway modifier — any address can call it.Always add onlyGateway to every Gateway callback function.
Callback fires but state not updatedRequest ID not stored — callback can't look up which proposal/auction to update.Store requestId → entityId mapping in requestDecryption() and look it up in the callback.
Test passes in mock, fails on devnetMock fires callback synchronously. Real Gateway is async (~2s). Test doesn't wait.In real-FHE tests, wait for the ResultRevealed event with a timeout: await contract.once("ResultRevealed", resolve).

Debug Patterns

Inspecting Handles

A handle is just a bytes32 value on-chain. In tests, you can read handles and inspect their metadata using the FHEVM SDK debug utilities:

TypeScriptHandle inspection in tests
import { getInstance } from "./helpers/fhevm";

// In test body:
const instance = await getInstance();

// Get the raw handle bytes32 from contract storage
const handleRaw: bigint = await contract.getCount();

// Decode handle metadata (available in local/mock mode)
if (process.env.HARDHAT_FHEVM_MOCK === "true") {
  // In mock mode, the "handle" actually encodes the plaintext value
  // You can read it directly without re-encryption:
  const plaintext = await instance.decryptMock(handleRaw);
  console.log("Mock plaintext:", plaintext);
}

// Check if a handle is zero (uninitialized)
function isZeroHandle(handle: bigint): boolean {
  return handle === 0n;
}

// Decode handle type bits (high byte of handle encodes the euintX size)
function getHandleType(handle: bigint): string {
  const typeByte = (handle >> 248n) & 0xffn;
  const typeMap: Record<number, string> = {
    0: "ebool", 1: "euint4", 2: "euint8", 3: "euint16",
    4: "euint32", 5: "euint64", 6: "euint128", 12: "eaddress"
  };
  return typeMap[Number(typeByte)] || `unknown(${typeByte})`;
}

// Usage in tests:
console.log("Handle type:", getHandleType(handleRaw));   // "euint32"
console.log("Is zero:",    isZeroHandle(handleRaw));       // false

Event Tracing for ACL Debug

The ACL contract emits events every time a grant is made. In a failing test, capturing these events tells you exactly which grants were made and which are missing:

TypeScriptACL event tracing helper
import { ethers } from "hardhat";

const ACL_ADDRESS = "0x339EcE85B9E11a3A3AA557582784a15d7F82AAf2";
const ACL_ABI = [
  "event Allowed(bytes32 indexed handle, address indexed account)",
  "event AllowedForAll(bytes32 indexed handle)",
  "function isAllowed(bytes32 handle, address account) view returns (bool)"
];

export async function traceACLGrants(txReceipt: any) {
  const acl = new ethers.Contract(ACL_ADDRESS, ACL_ABI, ethers.provider);
  const iface = acl.interface;

  console.log("\n  === ACL Grants in this tx ===");
  for (const log of txReceipt.logs) {
    try {
      const parsed = iface.parseLog(log);
      if (parsed?.name === "Allowed") {
        console.log(`  Allowed: handle=${parsed.args.handle.slice(0,10)}... → ${parsed.args.account}`);
      }
    } catch {} // ignore logs from other contracts
  }
}

// Check if a specific address has access to a handle
export async function checkACL(handle: bigint, address: string): Promise<boolean> {
  const acl = new ethers.Contract(ACL_ADDRESS, ACL_ABI, ethers.provider);
  return acl.isAllowed(handle, address);
}

Test Structure Best Practices

Unit Test Pattern — One Behavior Per Test

TypeScripttest/FHECounter.unit.test.ts
describe("FHECounter — Unit Tests", () => {
  let counter: any, owner: any, alice: any;
  let contractAddr: string;

  beforeEach(async () => {
    // Fresh deployment for each test — avoids state bleed
    [owner, alice] = await ethers.getSigners();
    const F = await ethers.getContractFactory("FHECounter");
    counter     = await F.deploy();
    contractAddr = await counter.getAddress();
  });

  // ✓ Test one behavior: ACL authorization
  it("getCount() reverts for unauthorized address", async () => {
    await expect(counter.connect(alice).getCount())
      .to.be.revertedWith("FHECounter: not authorized");
  });

  // ✓ Test one behavior: correct encryption binding
  it("add() with wrong contract address in proof reverts", async () => {
    // Encrypt for a DIFFERENT contract address (wrong binding)
    const { handles, inputProof } = await encUint32(
      42,
      "0x0000000000000000000000000000000000000001", // wrong address
      owner.address
    );
    await expect(counter.add(handles[0], inputProof))
      .to.be.reverted;  // KMSVerifier: invalid proof
  });

  // ✓ Test one behavior: state update after add
  it("add() increments txCount", async () => {
    const { handles, inputProof } = await encUint32(1, contractAddr, owner.address);
    await counter.add(handles[0], inputProof);
    expect(await counter.txCount()).to.equal(1n);
  });

  // ✓ Test one behavior: decrypt after single add
  it("add(42) → getCount() decrypts to 42", async () => {
    const { handles, inputProof } = await encUint32(42, contractAddr, owner.address);
    await counter.add(handles[0], inputProof);

    const handle    = await counter.connect(owner).getCount();
    const plaintext = await decryptHandle(handle, contractAddr, owner);
    expect(plaintext).to.equal(42n);
  });
});

Integration Test Pattern — Full Flow

TypeScripttest/FHEToken.integration.test.ts
describe("ConfidentialERC20 — Integration", () => {
  // Integration tests run with a shared contract across all tests
  // They test end-to-end flows: deploy → mint → transfer → verify
  let token: any, addr: string;
  let owner: any, alice: any, bob: any;

  before(async () => {
    [owner, alice, bob] = await ethers.getSigners();
    const F = await ethers.getContractFactory("ConfidentialERC20");
    token = await F.deploy("ConfCoin", "CONF");
    addr  = await token.getAddress();
  });

  it("FLOW: mint → transfer → verify balances → refund", async () => {
    // Step 1: Mint 1000 to alice
    await token.mint(alice.address, 1000n);

    // Step 2: Alice transfers 300 to bob
    const { handles: h, inputProof: p } = await encUint64(300n, addr, alice.address);
    await token.connect(alice).transfer(bob.address, h[0], p);

    // Step 3: Verify alice = 700
    const hA = await token.connect(alice).balanceOf(alice.address);
    expect(await decryptHandle(hA, addr, alice)).to.equal(700n);

    // Step 4: Verify bob = 300
    const hB = await token.connect(bob).balanceOf(bob.address);
    expect(await decryptHandle(hB, addr, bob)).to.equal(300n);

    // Step 5: Verify total supply unchanged
    expect(await token.totalSupply()).to.equal(1000n);
  });
});

Invariant Tests — Property-Based Checks

Define invariants — conditions that must always be true — and check them after every operation. These catch subtle bugs that targeted unit tests miss.

TypeScriptInvariant checker
/**
 * INVARIANT SUITE: ConfidentialERC20
 *
 * After every operation, all of these must hold:
 * 1. totalSupply == sum of all individual balances (when decryptable)
 * 2. No address has a negative balance (impossible but test for it)
 * 3. Allowances are always <= granter's balance at time of approval
 * 4. All balance handles have correct ACL grants
 */

async function checkInvariants(
  token: any,
  users: any[],
  addr: string
) {
  const expectedTotal = await token.totalSupply();
  let decryptedTotal = 0n;

  for (const user of users) {
    const handle  = await token.connect(user).balanceOf(user.address);
    const balance = await decryptHandle(handle, addr, user);
    decryptedTotal += balance;

    // Invariant: no negative balances (euint can't be negative, but verify)
    expect(balance).to.be.gte(0n);

    // Invariant: handle ACL — contract and user both have access
    expect(await checkACL(handle, addr))
      .to.be.true, `Contract lost ACL on ${user.address} balance`;
    expect(await checkACL(handle, user.address))
      .to.be.true, `User lost ACL on own balance`;
  }

  // Invariant: sum of balances == totalSupply
  expect(decryptedTotal).to.equal(expectedTotal,
    "Sum of decrypted balances does not match totalSupply"
  );
}

// Call after every state-changing operation:
it("invariants hold after mint + transfer", async () => {
  await token.mint(alice.address, 500n);
  await checkInvariants(token, [alice, bob], addr);

  const { handles: h, inputProof: p } = await encUint64(100n, addr, alice.address);
  await token.connect(alice).transfer(bob.address, h[0], p);
  await checkInvariants(token, [alice, bob], addr);
});

Day 10 Quiz — Week 2 Capstone
8 questions · Week 2 review
QUESTION 01 / 08
A test passes in mock mode but fails on Zama Devnet with "KMSVerifier: invalid proof". What is the most likely cause?
AThe contract compiled differently on devnet
BDevnet uses a different Solidity version
CMock mode skips ZK proof validation — the proof was generated with the wrong contract address or user address and only gets caught when real proof verification runs
DThe devnet gateway is not configured correctly
Correct — C. Mock mode skips fromExternal() proof verification entirely — any ciphertext passes. Real FHE mode verifies that the ZK proof binds the ciphertext to the exact contract address and msg.sender. A common bug is passing the wrong address to createEncryptedInput() which is invisible in mock mode.
QUESTION 02 / 08
Your test fails with "ACL: sender is not allowed" on the second call to a function, but the first call succeeds. What pattern should you check?
AMissing FHE.allowThis() after the FHE operation in the first call — the first call creates a new handle but doesn't grant the contract access, so the second call can't read it
BThe second call uses a different signer that wasn't registered
CThe ACL contract has a rate limit on permissions
DThe constructor's ACL grant expires after one use
Correct — A. The constructor may grant allowThis() on the initial handle, but the first operation creates a NEW handle. If you forget allowThis() on this new handle, the contract can't use it in the next transaction. First call works (using the initialized handle), second call fails (trying to use the new handle with no grants).
QUESTION 03 / 08
Why should FhevmInstance be a singleton (created once) across all tests rather than created fresh per test?
AMultiple instances would conflict with each other's state
BThe fhevmjs SDK only supports one instance per process
CEach instance generates a new encryption keypair, breaking previously encrypted values
DCreating an instance fetches the network's FHE public key from the node — an expensive network call that significantly slows down test runs if repeated for every test
Correct — D. createFhevmInstance() fetches the current FHE public key from the network, verifies KMS keys, and sets up the cryptographic context. This is a slow operation (100ms+) that involves network calls. Doing it once and caching the result is standard practice for fast test suites.
QUESTION 04 / 08
When should you use beforeEach (fresh deployment per test) vs before (shared deployment) for FHEVM contracts?
AAlways use beforeEach — state contamination in FHEVM is too risky
BUse beforeEach for unit tests that test single behaviors in isolation; use before for integration tests that deliberately test state accumulation across multiple operations
CAlways use before — redeployment invalidates cached encrypted inputs
DUse before if the contract has any encrypted state; beforeEach otherwise
Correct — B. Unit tests should be isolated — beforeEach gives a clean slate. Integration tests deliberately test multi-step flows (deploy → mint → transfer → verify) where state accumulation is intentional — before() is appropriate there. The key insight: unit tests test one thing; integration tests test sequences.
QUESTION 05 / 08
You want to test that a Gateway callback is called correctly after requestDecryption(). How should you wait for it in a real-FHE test?
Aawait sleep(5000) — just wait 5 seconds for the callback
BPoll contract.state() every 500ms until it changes
CListen for the event emitted by the callback: await new Promise(resolve => contract.once("ResultRevealed", resolve)) with a timeout
DThe Gateway callback always fires in the same block as requestDecryption() — no waiting needed
Correct — C. The canonical pattern for async Gateway tests is event-driven: listen for the event your callback emits, wrapped in a Promise with a timeout. Sleeping is fragile (timing-dependent), polling is wasteful, and assuming same-block delivery is wrong for real FHE where KMS processing takes ~2 seconds.
QUESTION 06 / 08
What does the handle type byte (high byte of the handle value) tell you during debugging?
AThe block number when the handle was created
BThe address of the contract that created the handle
CWhether the handle has been decrypted or not
DThe FHE type (ebool=0, euint8=2, euint32=4, euint64=5, etc.) — useful for verifying that fromExternal() correctly typed the ciphertext
Correct — D. The high byte of a handle encodes the encrypted type. During debugging, if you see an unexpected type byte, it means either: wrong input method was called (add32 instead of add64), or the handle was corrupted/zero. This is particularly useful when debugging "wrong size" type mismatches in cross-contract calls.
QUESTION 07 / 08
What is an invariant test in the context of FHEVM contracts, and what bug class does it catch?
AA test that verifies properties that must always hold true (e.g., sum of balances == totalSupply, all handles have allowThis()) — catches subtle state corruption that targeted tests miss
BA test that checks that the contract code cannot be modified after deployment
CA test that verifies FHE operations produce consistent results across multiple calls
DA test that verifies the contract's constructor runs without reverting
Correct — A. Invariant tests define global correctness conditions — things that must be true in every valid state regardless of how you got there. For FHEVM, key invariants include: sum of decryptable balances matches totalSupply, no uninitialized handles (zero handle), all stored handles have allowThis(), Gateway callbacks have onlyGateway. These catch bugs that unit tests miss because they verify systemic properties.
QUESTION 08 / 08
Why must you never cache encrypted inputs (handles + inputProof) across contract deployments?
AThe fhevmjs SDK uses a session token that expires
BThe ZK proof is cryptographically bound to the contract address — when the contract redeploys to a new address, the old proof is bound to the old address and will always fail the fromExternal() verification in the new contract
CThe ciphertext format changes between deployments
DThe KMS rotates its public key on each new deployment
Correct — B. fromExternal() verifies that the ZK proof was generated for this specific contract address + caller address. Redeployment creates a new contract at a new address. Any proof generated for the old address will fail verification at the new address. Always call createEncryptedInput(newContractAddr, callerAddr) after every redeployment.
