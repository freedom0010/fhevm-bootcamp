The Gateway is FHEVM's bridge between encrypted on-chain state and plaintext results. When you need a contract to act on decrypted values — finalizing an auction, settling a game, triggering a liquidation — you go through the Gateway. Why a Gateway?

FHE ciphertexts can be computed on (add, multiply, compare) without decryption. But sometimes a contract needs the actual plaintext — to branch its logic, emit a result, trigger a payout, or make a public announcement. Decrypting directly in the EVM is impossible (the KMS holds the secret key). The Gateway is the trusted intermediary that:

  • Receives a decryption request from a smart contract
  • Forwards it to the KMS (multi-party key management service)
  • Delivers the plaintext result back to the contract via a callback transaction
🔒
Re-encryption vs Public Decryption
Re-encryption (user views own data): The KMS re-encrypts the ciphertext under the user's ephemeral public key. Plaintext never appears on-chain. Used for balance queries, private data views.

Public decryption (Gateway callback): The KMS decrypts and the Gateway sends plaintext to your contract callback. The plaintext appears in the callback transaction's calldata — visible to everyone. Use only when you intend to make the value public (auction winner, game result, tally).

End-to-End Decryption Flow

1

Contract calls Gateway.requestDecryption(handles[], callbackSelector, 0, deadline, false)

The Gateway emits a DecryptionRequest event with a unique requestId. Returns the requestId for tracking.

2

KMS monitors the Gateway for events

KMS nodes observe the blockchain for DecryptionRequest events. They fetch the ciphertexts from the coprocessor.

3

KMS threshold decryption

Multiple KMS nodes independently decrypt (threshold scheme). They reach consensus and generate a signed plaintext result.

4

Gateway submits callback transaction

Gateway calls your contract's callback function (identified by callbackSelector) with the plaintext values. Typically takes 1–5 seconds on Devnet, up to 30s on Sepolia.

5

Your callback function executes

Receives (uint256 requestId, T1 val1, T2 val2, ...). The onlyGateway modifier verifies the sender is the legitimate Gateway. You finalize state: set winner, trigger payout, update result.

Requesting Multiple Types

You can decrypt up to several handles in one request. The callback receives them as positional parameters in declaration order. Mix types freely — the callback signature must match exactly.

SolidityMulti-type decryption request
function revealAuctionResult() external onlyOwner {
    FHE.makePubliclyDecryptable(_winningBid);     // euint64
    FHE.makePubliclyDecryptable(_winnerAddress);  // eaddress
    FHE.makePubliclyDecryptable(_winnerScore);    // euint32

    uint256[] memory handles = new uint256[](3);
    handles[0] = euint64.unwrap(_winningBid);
    handles[1] = eaddress.unwrap(_winnerAddress);
    handles[2] = euint32.unwrap(_winnerScore);

    uint256 reqId = Gateway.requestDecryption(
        handles,
        this.auctionResultCallback.selector,
        0,
        block.timestamp + 1 hours,
        false
    );
    _pendingRequestId = reqId;
    state = State.Settling;
}

// Callback: parameters match request order exactly
// uint256 requestId is ALWAYS the first parameter
function auctionResultCallback(
    uint256 requestId,   // always first
    uint64  winningBid,  // handles[0] — euint64 → uint64
    address winner,     // handles[1] — eaddress → address
    uint32  score        // handles[2] — euint32 → uint32
) external onlyGateway {
    require(requestId == _pendingRequestId, "Wrong request");
    // Handle the results...
    _finalBid    = winningBid;
    _finalWinner = winner;
    _finalScore  = score;
    state        = State.Settled;
    emit ResultRevealed(winner, winningBid, score);
}

Callback Patterns

The onlyGateway Modifier

⚠
Always Use onlyGateway on Callbacks
Without onlyGateway, any address can call your callback with fake plaintext values. An attacker could call auctionResultCallback(requestId, 999999, attackerAddress, 255) and set themselves as the winner. onlyGateway checks msg.sender == GatewayContractAddress — only the legitimate Gateway can deliver results.
SolidityonlyGateway source (from GatewayCaller.sol)
// What onlyGateway actually does (simplified):
modifier onlyGateway() {
    require(
        msg.sender == address(Gateway),
        "GatewayCaller: caller is not the Gateway"
    );
    _;
}

State Machine Pattern for Async Flow

SolidityFull async state machine
contract AsyncReveal is ZamaEthereumConfig, GatewayCaller {

    enum State { Active, PendingReveal, Revealed }
    State public state = State.Active;

    euint64  private _secret;
    uint64   public  revealedValue;
    uint256  private _pendingRequest;

    // Step 1: initiate decryption
    function requestReveal() external {
        require(state == State.Active, "Not active");
        state = State.PendingReveal; // ← lock state to prevent re-entry

        FHE.makePubliclyDecryptable(_secret);

        uint256[] memory handles = new uint256[](1);
        handles[0] = euint64.unwrap(_secret);

        _pendingRequest = Gateway.requestDecryption(
            handles,
            this.revealCallback.selector,
            0,
            block.timestamp + 2 hours,
            false
        );
    }

    // Step 2: Gateway delivers result
    function revealCallback(
        uint256 requestId,
        uint64  value
    ) external onlyGateway {
        require(requestId == _pendingRequest, "Unexpected request");
        require(state == State.PendingReveal, "Wrong state");

        revealedValue = value;
        state         = State.Revealed;
        emit ValueRevealed(value);
    }

    // Guard: prevent reveal being called twice
    function getSecret() external view returns (uint64) {
        require(state == State.Revealed, "Not revealed yet");
        return revealedValue;
    }
}

Timeout & Retry

⏰
Gateway Callbacks Are Not Guaranteed
The Gateway callback is delivered eventually by Zama infrastructure — it is not atomic with your request. If the KMS is down, the network is congested, or the deadline passes, the callback may never arrive. Design for this:

• Set generous deadlines (block.timestamp + 2 hours for non-urgent, + 24 hours for auction settlements)
• Implement a retryRequest() function that can re-submit if the deadline passes
• Use a PendingReveal state to prevent double-requests
• Consider timeout-recovery paths (e.g., if no result after 24h, allow users to reclaim funds)
SolidityTimeout recovery pattern
uint256 public  requestDeadline;
uint256 private _pendingRequest;

function requestReveal() external {
    require(state == State.Active, "Not active");
    state = State.PendingReveal;
    requestDeadline = block.timestamp + 2 hours;
    // ... request decryption ...
}

// If callback never arrives, admin can retry after deadline
function retryReveal() external onlyOwner {
    require(state == State.PendingReveal, "Not pending");
    require(block.timestamp > requestDeadline, "Deadline not passed");
    // Reset to allow a fresh request
    state = State.Active;
    requestReveal(); // re-submit
}

// Emergency escape: if KMS is permanently unavailable
function emergencyRefund() external {
    require(state == State.PendingReveal);
    require(block.timestamp > requestDeadline + 24 hours);
    // Allow all participants to withdraw their deposits
    state = State.Cancelled;
}

Multiple Pending Requests

In complex protocols (e.g., multiple auctions running in parallel), you may have several pending Gateway requests simultaneously. Use a mapping to track them:

SolidityMultiple concurrent Gateway requests
// Map requestId → auctionId for parallel auctions
mapping(uint256 => uint256) private _requestToAuction;

function closeAuction(uint256 auctionId) external {
    Auction storage a = auctions[auctionId];
    require(a.state == State.Active && block.timestamp >= a.deadline);

    FHE.makePubliclyDecryptable(a.highestBid);
    FHE.makePubliclyDecryptable(a.highestBidder);

    uint256[] memory handles = new uint256[](2);
    handles[0] = euint64.unwrap(a.highestBid);
    handles[1] = eaddress.unwrap(a.highestBidder);

    uint256 reqId = Gateway.requestDecryption(
        handles, this.auctionCallback.selector,
        0, block.timestamp + 2 hours, false
    );

    _requestToAuction[reqId] = auctionId;  // track which auction
    a.state = State.Settling;
}

function auctionCallback(
    uint256 requestId, uint64 bid, address winner
) external onlyGateway {
    uint256 auctionId = _requestToAuction[requestId];
    auctions[auctionId].finalBid    = bid;
    auctions[auctionId].winner      = winner;
    auctions[auctionId].state       = State.Settled;
    emit AuctionSettled(auctionId, winner, bid);
}

Testing Async Callbacks

Local Hardhat + the FHEVM mock Gateway fires callbacks automatically in the same block. No need to wait or poll. On production networks, you need to wait for the async callback:

TypeScriptTesting Gateway callbacks on Hardhat vs Devnet
import { awaitAllDecryptionResults } from "@fhevm/hardhat-plugin";

it("reveals value via Gateway callback", async () => {
  // Trigger the decryption request
  const tx = await contract.requestReveal();
  await tx.wait();

  // On local Hardhat: this processes all pending mock Gateway callbacks
  // On Devnet/Sepolia: this polls until the real callback arrives (timeout: 30s)
  await awaitAllDecryptionResults();

  // Callback has now been delivered — verify state
  expect(await contract.state()).to.equal(2); // State.Revealed
  const val = await contract.getSecret();
  console.log("  Revealed value:", val.toString());
  expect(val).to.be.greaterThan(0n);
});

// For multiple parallel requests:
it("settles two auctions concurrently", async () => {
  await auction.closeAuction(0);
  await auction.closeAuction(1);

  // awaitAllDecryptionResults handles BOTH pending callbacks
  await awaitAllDecryptionResults();

  expect((await auction.auctions(0)).state).to.equal(3); // Settled
  expect((await auction.auctions(1)).state).to.equal(3); // Settled
});

QUESTION 01 / 08
What is the difference between re-encryption (user views own balance) and public decryption (Gateway callback)?
ARe-encryption is faster; public decryption uses a different key
BRe-encryption uses the Gateway; public decryption bypasses it
CRe-encryption delivers plaintext only to the user (encrypted under their key, decrypted locally — never on-chain); public decryption delivers plaintext to the contract via a callback where it becomes visible in calldata to all
DThey are identical — both routes deliver plaintext to the contract
Correct — C. Re-encryption is privacy-preserving: the KMS re-encrypts under the user's ephemeral key, user decrypts locally, plaintext stays client-side. Public decryption via Gateway makes the value visible to everyone in the callback transaction's calldata. Use Gateway only when you INTEND to make data public.
QUESTION 02 / 08
Why must FHE.makePubliclyDecryptable(handle) be called before Gateway.requestDecryption()?
AIt converts the handle from encrypted to plaintext format for the Gateway
BIt sets the ACL flag that authorizes the KMS to decrypt this handle for anyone — without it, the KMS would reject the decryption request as unauthorized
CIt locks the handle so no further FHE operations can modify it before decryption
DIt signals the coprocessor to finalize the computation result
Correct — B. makePubliclyDecryptable() writes a flag in the ACL marking the handle as publicly decryptable. The KMS checks this ACL before performing decryption. Without it, the KMS sees that the handle is not marked for public decryption and rejects the request. Remember: this flag is irreversible.
QUESTION 03 / 08
An attacker calls your callback function directly with fake plaintext values. What prevents this?
AThe requestId is unknown to attackers
BOnly encrypted contracts can call callback functions
CThe callback parameters are automatically validated by the EVM
DThe onlyGateway modifier checks msg.sender == Gateway contract address — only the legitimate on-chain Gateway contract can call it, and the Gateway only calls it after receiving validated KMS signatures
Correct — D. onlyGateway is the critical security check. RequestIds are on-chain events (public), so knowing one doesn't help. Without onlyGateway, any address could call your callback with fabricated results — declaring themselves the winner, setting fake values, etc. Always use onlyGateway on ALL callback functions.
QUESTION 04 / 08
In a callback function that receives results for multiple handles, what is the first parameter?
Auint256 requestId — always the first parameter in every Gateway callback, regardless of how many handles are being decrypted
BThe first decrypted value in the handles array
CThe address of the original requester
DA boolean indicating success or failure
Correct — A. Gateway callback convention: the first parameter is ALWAYS uint256 requestId. This lets you match the callback to the correct pending request (especially important for parallel requests). After requestId come the decrypted values in the same order as you supplied handles in the request array.
QUESTION 05 / 08
Why should your contract transition to a "PendingReveal" state (or equivalent) when calling requestDecryption?
AThe Gateway requires the contract to be in a specific state
BTo prevent the KMS from processing the request until ready
CTo prevent duplicate requests — if someone calls requestDecryption again while a callback is pending, the state check rejects it. Also prevents state from being modified between the request and the callback
DThe Gateway reads the contract state to validate the request
Correct — C. The state machine pattern is essential for async safety. Between your request (Tx A) and the callback (Tx B), other transactions can modify your contract. Setting PendingReveal prevents: (1) double requests via the same function, (2) state changes that would invalidate the pending decryption, (3) race conditions in multi-step flows.
QUESTION 06 / 08
You have 5 auctions running in parallel. Each calls closeAuction() and gets a different requestId. What mechanism routes each callback to the correct auction?
AThe Gateway sends a different callback selector per auction
BA mapping(uint256 requestId => uint256 auctionId) lets the callback look up which auction each requestId corresponds to
CThe callback receives the auctionId as a hidden extra parameter
DYou need a separate callback function per auction
Correct — B. Store the mapping when you submit the request: _requestToAuction[reqId] = auctionId. In the callback, look it up: uint256 auctionId = _requestToAuction[requestId]. This pattern scales to any number of parallel requests with one shared callback function.
QUESTION 07 / 08
What happens if the Gateway callback never arrives (KMS downtime, network issue)?
AThe request is automatically retried by the Gateway after 1 hour
BThe ciphertext is automatically decrypted using a backup key
CThe contract reverts to its pre-request state automatically
DYour contract stays stuck in PendingReveal forever unless you implement a timeout recovery — a retryReveal() function that checks block.timestamp > deadline and resubmits, plus an emergency escape hatch for prolonged outages
Correct — D. There's no automatic retry — your contract design must handle this. Best practice: retryReveal() callable after deadline passes (requiring onlyOwner), and an emergencyRefund() callable after a much longer period (e.g., 7 days) that lets users reclaim their funds if the system is permanently down.
QUESTION 08 / 08
How does awaitAllDecryptionResults() from @fhevm/hardhat-plugin work differently on local Hardhat vs production Devnet?
AOn Hardhat: it triggers the mock Gateway to synchronously process all pending callbacks in the test. On Devnet: it polls the blockchain for the real KMS callback transaction until it appears or times out (~30s)
BIt works identically on both — just waits 2 seconds
COn Hardhat: it skips the Gateway step entirely. On Devnet: it simulates the KMS
DIt only works on Hardhat — Devnet requires manual waiting
Correct — A. The hardhat-plugin provides a mock Gateway that runs in-process. awaitAllDecryptionResults() triggers it to synchronously deliver all pending callbacks — making async flows testable as regular synchronous tests. On Devnet, the real KMS is used and the function polls for the callback transaction to arrive on-chain.
