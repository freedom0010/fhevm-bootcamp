Gas Optimization
for Encrypted Ops

FHE operations are 100–1000× more expensive than their plaintext equivalents. A naively written transfer can cost 600k gas; an optimized one costs 260k. In production, this difference determines whether your DApp is usable. Today you learn the six rules that cut encrypted contract gas by 30–60%: batching, preferring native min/max, right-sizing types, caching handles, batching ACL grants, and multicall aggregation.

The FHE Cost Model

Standard Solidity gas costs scale with storage writes and computation complexity. FHEVM adds a new dimension: every homomorphic operation dispatches a task to the off-chain coprocessor and writes a new handle to the ACL. Each FHE op has a fixed base cost regardless of how it's used.

The Golden Rule
Every FHE operation that can be eliminated or combined saves 30k–300k gas. Think of each TFHE call as a database query — design your contract logic to minimize the number of encrypted operations per transaction, just as you would minimize SQL queries in a hot path.

Rule 1 — Batch Operations in One Transaction

Each transaction has a fixed overhead for contract calls and ACL bookkeeping. Grouping multiple FHE operations into a single transaction amortizes this overhead and, more importantly, keeps all allowTransient calls valid within the same execution context.

Batch vs Separate Transactions

✘ Expensive — 3 separate txs (~195k + ~195k + ~195k = 585k gas total)
// 3 separate user transactions
token.transfer(alice, encAmt1, proof1)   // tx 1
token.transfer(bob,   encAmt2, proof2)   // tx 2
token.transfer(carol, encAmt3, proof3)   // tx 3
✓ Optimized — 1 multicall tx (~450k, saves ~35%)
// One multicall batches all three
multicall([
  encodeTransfer(alice, encAmt1, proof1),
  encodeTransfer(bob,   encAmt2, proof2),
  encodeTransfer(carol, encAmt3, proof3),
])

The savings come from: one base transaction cost (~21k gas), warm contract storage access after the first call, and shared ACL contract state writes.

Rule 2 — Prefer Native min/max Over gt + select

A common pattern for clamping values is TFHE.gt(a, cap) followed by TFHE.select(isTooLarge, cap, a). This is two coprocessor calls. TFHE.min(a, cap) does the same thing in one internal operation.

min/max vs Manual Clamp

✘ 2 ops — gt (~65k) + select (~45k) = ~110k gas
ebool tooBig = TFHE.gt(amount, cap);
euint64 safe = TFHE.select(tooBig, cap, amount);
// Two separate coprocessor tasks
✓ 1 op — TFHE.min (~80k) saves ~30k gas
euint64 safe = TFHE.min(amount, cap);
// One coprocessor task — use for all clamp patterns
💡
min/max Cheat Sheet
Use TFHE.min(a, b) for clamping to a maximum (cap). Use TFHE.max(a, b) to guarantee a minimum value (floor). Both are cheaper than the equivalent compare + select pair. For the common "safe transfer" pattern, TFHE.min(balance, requested) is the canonical form.

Rule 3 — Use the Narrowest Type That Fits

Counterintuitively, FHE operations do not cost more for wider types (euint64 vs euint8 costs the same). However, type width matters for input verification: verifying a euint8 input is faster than euint64 because the ZK proof is smaller. The real savings from narrow types come from avoiding unnecessary widening casts mid-computation.

Type Width Cost Table

📋
Rule of Thumb
Choose the type based on domain range, not gas. Use euint64 for most token amounts (matches Solidity's uint64 and avoids overflow). Avoid unnecessary widening casts — each TFHE.asEuint64(euint32) is a ~30k gas operation. Plan your type widths at contract design time.

Rule 4 — Cache Intermediate Results

Every time you reference _balances[addr] in a computation, you're reading the handle from storage (cold: 2100 gas, warm: 100 gas). But if you call a TFHE operation on it twice, each call creates a new coprocessor task. Cache the result of expensive operations in local variables.

Cache Pattern

✘ Recomputes add twice — wastes ~65k gas
// Each TFHE.add is a separate coprocessor call
_logs[user] = TFHE.add(_balances[user], amt);
emit Transfer(_balances[user], // re-reads handle
              TFHE.add(_balances[user], amt)); // NEW op!
✓ Cache the result — one add, reused everywhere
// Compute once, reference the handle multiple times
euint64 newBal = TFHE.add(_balances[user], amt);
_balances[user] = newBal;
_logs[user]     = newBal;  // same handle, no new op
TFHE.allow(newBal, user);  // still one allow

Rule 5 — Batch ACL Grants

TFHE.allow(handle, addr) costs ~22k gas per call (one SSTORE in the ACL contract). When you update multiple values for multiple addresses, grant order and batching matters. Grant all permissions for a handle before moving to the next to keep ACL contract storage warm.

ACL Batch Code

✘ Interleaved — cold storage access pattern
TFHE.allow(senderBal, msg.sender);
TFHE.allow(recipientBal, recipient);
TFHE.allow(senderBal, address(this));   // cold again
TFHE.allow(recipientBal, address(this)); // cold again
✓ Grouped — warm storage saves ~1.2k gas each
// All grants for senderBal while it's warm
TFHE.allow(senderBal, msg.sender);
TFHE.allow(senderBal, address(this));
// Then all grants for recipientBal
TFHE.allow(recipientBal, recipient);
TFHE.allow(recipientBal, address(this));

Additionally, use TFHE.allowTransient instead of TFHE.allow for same-transaction cross-contract calls — transient storage is ~10× cheaper (2k vs 22k gas per grant).

Rule 6 — Aggregate with Multicall

For admin or batch operations (e.g., airdrop to 100 addresses), a custom batchTransfer function that loops internally is far cheaper than 100 individual transfer transactions. The savings are primarily from transaction base cost (21k gas) and warm contract state access.

Batch Transfer Pattern

Solidity
contracts/ConfidentialERC20.sol — batchTransfer
struct TransferOp {
    address to;
    bytes32 encryptedAmount;
    bytes   inputProof;
}

/**
 * @dev Batch transfer: execute N transfers in one tx.
 *      Per-recipient savings: ~21k (base tx cost) + ~5k (warm contract storage).
 *      For 10 recipients: ~260k gas vs ~2.6M for 10 separate txs.
 *      Gas limit: keep N ≤ 20 to stay under the block gas limit.
 */
function batchTransfer(TransferOp[] calldata ops) external {
    require(ops.length <= 20, "Max 20 per batch");

    // Cache sender balance handle — one cold SLOAD, then all warm
    euint64 senderBalance = _balances[msg.sender];
    TFHE.allow(senderBalance, address(this));

    for (uint i = 0; i < ops.length; i++) {
        euint64 amt = TFHE.asEuint64(ops[i].encryptedAmount, ops[i].inputProof);

        // Clamp to available balance (safe transfer pattern)
        euint64 toSend = TFHE.min(amt, senderBalance);

        // Update balances
        senderBalance        = TFHE.sub(senderBalance, toSend);
        euint64 newRecipient = TFHE.add(_balances[ops[i].to], toSend);
        _balances[ops[i].to] = newRecipient;

        // ACL: group grants for newRecipient while warm
        TFHE.allow(newRecipient, ops[i].to);
        TFHE.allow(newRecipient, address(this));

        emit Transfer(msg.sender, ops[i].to);
    }

    // Write final sender balance once (not N times)
    _balances[msg.sender] = senderBalance;
    TFHE.allow(senderBalance, msg.sender);
    TFHE.allow(senderBalance, address(this));
}
⚠
Block Gas Limit
Each FHE operation dispatches a coprocessor task. Very large batches can cause the transaction to exceed the block gas limit (~30M on Zama Devnet). Keep batches to ≤ 20 FHE-heavy operations per transaction. Test your gas usage with hardhat-gas-reporter before deploying.

QUESTION 01 / 06
Why does TFHE.add(a, b) cost ~65,000 gas regardless of whether a is a euint8 or euint64?
ASolidity pads all integer types to 256 bits internally
BThe FHE base cost is determined by the coprocessor dispatch overhead, which is fixed per operation — the plaintext bit-width of the type does not change this dispatch cost
CThe ACL contract charges a flat 65k fee for all encrypted writes
DThe EVM internally converts all FHEVM types to uint256 before processing
Correct — B. The gas is dominated by the coprocessor task dispatch and ACL handle management overhead — both fixed costs independent of type width. Input verification (the ZK proof check) scales slightly with type width, but arithmetic operations themselves do not.
QUESTION 02 / 06
You want to cap a transfer amount to the sender's available balance. Which pattern is most gas-efficient?
Aebool ok = TFHE.ge(balance, amount); TFHE.select(ok, amount, balance)
BTFHE.asEuint64(balance) > amount ? amount : balance
CTFHE.min(amount, balance)
DRequest Gateway decryption of the balance, then compare in plaintext
Correct — C. TFHE.min is one coprocessor call (~80k gas). Option A requires two calls: ge (~65k) + select (~45k) = ~110k. Option B uses a Solidity comparison on an ebool which doesn't compile. Option D introduces async latency and defeats the purpose of encrypted operations.
QUESTION 03 / 06
When should you use TFHE.allowTransient instead of TFHE.allow?
AWhen you want the permission to last for 1 day
BWhen the receiving contract is on a different chain
CWhen the user's wallet needs to sign the permission
DWhen the permission only needs to last for the current transaction — for example, granting a router contract access to pass a handle to another contract in the same call chain
Correct — D. allowTransient uses EIP-1153 transient storage which is cleared at the end of each transaction (~2k gas vs ~22k for persistent). Use it for same-transaction cross-contract composability. Use persistent allow when the grantee needs to access the handle in a future transaction.
QUESTION 04 / 06
You compute euint64 newBal = TFHE.add(_balances[user], amt) and then need to store it and grant two ACL permissions. How many coprocessor calls does this represent?
AOne — the add creates one new handle; storing and allowing it just reference the same handle without new coprocessor calls
BThree — one per operation (add, store, allow)
CTwo — one for the add and one for the combined storage + ACL
DFour — the ACL grants each trigger a coprocessor verification
Correct — A. TFHE.add is the only coprocessor call. The resulting newBal is a handle (uint256). Writing it to storage and calling TFHE.allow(newBal, addr) twice just reference this handle — no additional FHE computation occurs.
QUESTION 05 / 06
Why is TFHE.div (~300k gas) particularly expensive compared to TFHE.add (~65k)?
ADivision requires a Gateway decryption request
BDivision in TFHE requires a more complex garbled circuit in the coprocessor — it cannot be expressed as a simple polynomial evaluation and requires more bootstrapping operations
CThe ACL charges more for quotient handles
DDivision triggers a ZK proof re-generation on the coprocessor
Correct — B. Addition and comparison map efficiently to polynomial arithmetic over the TFHE ring. Division requires a more complex computation — equivalent to multiple bootstrapping operations — driving the cost ~5× higher. When possible, replace division with pre-computed inverses or shift operations.
QUESTION 06 / 06
You have a batchTransfer(TransferOp[] ops) for 10 recipients. Approximately how much gas does this save vs 10 separate transfer transactions at ~260k gas each?
ANo savings — each transfer still requires the same FHE operations
B~50k total savings
C~1.4M gas savings — the batch costs ~1.2M vs ~2.6M for 10 individual transactions
D~5M gas savings
Correct — C. 10 separate txs: 10 × 260k = ~2.6M gas. A batch tx: ~120k per transfer (warm state, shared base cost) × 10 = ~1.2M gas. Savings: ~1.4M (~54%). The key savings are: one 21k base tx cost shared, warm contract storage access, and cached sender balance handle avoiding repeated cold SLOADs.
