Async Decryption

In FHEVM, decryption is never instantaneous. A request goes on-chain, the KMS cluster signs a threshold decryption, and the result is delivered back via a callback transaction — potentially seconds or blocks later. Mastering this async pattern is essential for building auctions, voting systems, and any contract that publicly reveals encrypted results. Today you learn every variant: single-value reveal, batch, conditional, and how to keep your frontend in sync.

Why is Decryption Always Async?

Decryption requires the KMS — a threshold MPC cluster of independent nodes that must each sign the decryption before a result is released. This consensus round cannot happen within a single Ethereum block's execution. Instead, FHEVM uses a two-transaction model:

  • Transaction 1 — Your contract calls Gateway.requestDecryption(), emitting an event that the KMS monitors.
  • KMS processing — Nodes jointly compute the threshold decryption and sign the result.
  • Transaction 2 — The Gateway submits the decrypted plaintext back to your contract's callback function.
⚠
Never Try to Read Decryption Synchronously
You cannot know the decrypted value in the same transaction as the request. Any contract that attempts to use a decrypted value synchronously is broken by design. Always split into request + callback.

Decryption Lifecycle

1

Contract calls allowForDecryption(handle)

Grants the Gateway permission to decrypt the handle. Must be called before or in the same tx as the request.

2

Contract calls Gateway.requestDecryption(...)

Registers the request on-chain. The callback selector, request ID, and encrypted handles are stored in Gateway state.

3

KMS monitors the Gateway event

Off-chain KMS nodes detect the EventDecryption event, reach threshold consensus, sign the plaintext result.

4

Gateway calls your callback

Gateway contract invokes yourContract.callbackName(requestId, plaintext). Your contract handles the revealed value.

5

Frontend detects callback event

Watch for your contract's ResultRevealed (or similar) event to update the UI without polling.

The Gateway Contract

The Gateway is a pre-deployed system contract. You interact with it through the GatewayLib helper that ships with fhevm/lib/GatewayLib.sol. You never deploy the Gateway yourself.

requestDecryption Signature

Solidity
GatewayLib reference
// Simplified signature (from fhevm/lib/GatewayLib.sol)
function requestDecryption(
    uint256[] calldata ciphertextHandles,  // handles to decrypt
    bytes4   callbackSelector,            // your callback function selector
    uint256  msgValue,                    // ETH to forward to callback (usually 0)
    uint256  maxTimestamp,                // deadline for KMS response
    bool     passSignaturesToCaller       // true = KMS sigs forwarded to callback
) external returns (uint256 requestID)

Callback Function Rules

Your callback function must follow a strict signature pattern:

  • First parameter: uint256 requestID
  • Remaining parameters: one plaintext value per handle requested, in the same order
  • Must be marked external
  • Must use the onlyGateway modifier to prevent spoofing
🚫
Always Use onlyGateway
Without onlyGateway, any address can call your callback with forged plaintext values. The modifier verifies the caller is the official Gateway contract address.

Pattern 1 — Single Value Reveal

The simplest case: reveal one encrypted value after a condition is met (e.g., auction ends).

Auction Winner Reveal

Solidity
contracts/SealedAuction.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "fhevm/lib/TFHE.sol";
import "fhevm/gateway/GatewayLib.sol";
import "fhevm/gateway/GatewayLib.sol";

contract SealedAuction {
    using GatewayLib for GatewayLib.Gateway;

    euint64  private _highestBid;
    address  public  highestBidder;
    bool     public  auctionEnded;
    bool     public  resultRevealed;
    uint64   public  revealedWinningBid;

    // requestID → bidder (so callback can store result)
    mapping(uint256 => address) private _pendingReveal;

    event AuctionEnded(address indexed winner);
    event BidRevealed(address indexed winner, uint64 amount);

    modifier onlyGateway() {
        require(msg.sender == GatewayLib.gatewayContractAddress(), "Only gateway");
        _;
    }

    function endAuction() external {
        require(!auctionEnded, "Already ended");
        auctionEnded = true;

        // Grant Gateway permission to decrypt the winning bid
        TFHE.allowForDecryption(_highestBid);

        uint256[] memory handles = new uint256[](1);
        handles[0] = euint64.unwrap(_highestBid);

        // Request decryption — callback is revealCallback(uint256, uint64)
        uint256 reqId = GatewayLib.requestDecryption(
            handles,
            this.revealCallback.selector,
            0,             // no ETH forwarded
            block.timestamp + 1 days,
            false
        );
        _pendingReveal[reqId] = highestBidder;

        emit AuctionEnded(highestBidder);
    }

    /// @dev Called by the Gateway after KMS decrypts the winning bid
    function revealCallback(uint256 requestId, uint64 winningBid)
        external onlyGateway
    {
        address winner = _pendingReveal[requestId];
        delete _pendingReveal[requestId];

        revealedWinningBid = winningBid;
        resultRevealed = true;

        emit BidRevealed(winner, winningBid);
    }
}

Pattern 2 — Multi-Value Batch Decrypt

You can request decryption of up to several handles in a single call. All plaintext values are delivered together in one callback invocation.

Batch Decryption Example

Solidity
contracts/VotingResult.sol (excerpt)
// Reveal yes votes + no votes in one batch request
function revealResults() external {
    require(block.timestamp > votingEnd, "Voting ongoing");

    TFHE.allowForDecryption(_yesVotes);
    TFHE.allowForDecryption(_noVotes);

    uint256[] memory handles = new uint256[](2);
    handles[0] = euint32.unwrap(_yesVotes);
    handles[1] = euint32.unwrap(_noVotes);

    GatewayLib.requestDecryption(
        handles,
        this.resultsCallback.selector,
        0,
        block.timestamp + 1 days,
        false
    );
}

/// @dev Callback receives BOTH plaintext values at once
function resultsCallback(
    uint256 /* requestId */,
    uint32 yesCount,
    uint32 noCount
) external onlyGateway {
    revealedYes = yesCount;
    revealedNo  = noCount;
    resultsPublished = true;
    emit ResultsPublished(yesCount, noCount);
}
💡
Order Matters
The plaintext parameters in your callback must be in the same order as the handles in the ciphertextHandles array. Mixing up the order silently assigns the wrong values.

Pattern 3 — Conditional Reveal

Sometimes you want to reveal a value only if an encrypted condition is true — for example, "reveal the salary only if both parties have signed". You cannot branch on encrypted conditions synchronously, but you can compute an encrypted boolean, then reveal the result value only after decrypting the condition first.

Solidity
contracts/ConditionalReveal.sol (excerpt)
// Phase 1: request decryption of the CONDITION (ebool)
function requestConditionCheck() external {
    TFHE.allowForDecryption(_bothSigned);
    uint256[] memory h = new uint256[](1);
    h[0] = ebool.unwrap(_bothSigned);
    GatewayLib.requestDecryption(h, this.conditionCallback.selector, 0,
                                  block.timestamp + 1 days, false);
}

// Phase 2: only if condition is true, request the value reveal
function conditionCallback(uint256 /* reqId */, bool bothSigned)
    external onlyGateway
{
    if (!bothSigned) {
        emit RevealDenied();
        return;
    }
    // Now safe to reveal the value
    TFHE.allowForDecryption(_salary);
    uint256[] memory h = new uint256[](1);
    h[0] = euint64.unwrap(_salary);
    GatewayLib.requestDecryption(h, this.salaryCallback.selector, 0,
                                  block.timestamp + 1 days, false);
}

function salaryCallback(uint256 /* reqId */, uint64 salary)
    external onlyGateway
{
    revealedSalary = salary;
    emit SalaryRevealed(salary);
}

Frontend: Watching for the Callback

Because decryption is async, your UI must listen for the callback completion rather than waiting on a single transaction. The cleanest approach is event-driven using wagmi's watchContractEvent.

What Events to Watch

Emit a dedicated event in your callback (e.g., BidRevealed, ResultsPublished) and have the frontend subscribe before triggering the request. This avoids race conditions.

Wagmi watchContractEvent Pattern

TypeScript
hooks/useAuctionResult.ts
import { useState, useEffect } from 'react'
import { useConfig, useWriteContract } from 'wagmi'
import { watchContractEvent } from 'wagmi/actions'
import { AUCTION_ADDRESS, AUCTION_ABI } from '../lib/contract'

export function useAuctionResult() {
  const [result, setResult] = useState<{
    winner: string; amount: bigint
  } | null>(null)
  const [waiting, setWaiting] = useState(false)
  const config = useConfig()
  const { writeContract } = useWriteContract()

  useEffect(() => {
    // Subscribe to BidRevealed event
    const unwatch = watchContractEvent(config, {
      address: AUCTION_ADDRESS,
      abi: AUCTION_ABI,
      eventName: 'BidRevealed',
      onLogs: (logs) => {
        const log = logs[0]
        setResult({ winner: log.args.winner!, amount: log.args.amount! })
        setWaiting(false)
      },
    })
    return () => unwatch()
  }, [config])

  async function endAuction() {
    setWaiting(true)
    writeContract({
      address: AUCTION_ADDRESS,
      abi: AUCTION_ABI,
      functionName: 'endAuction',
    })
    // BidRevealed event fires in a later block — useEffect handles it
  }

  return { result, waiting, endAuction }
}
📋
Typical Callback Latency
On Zama Devnet, the KMS typically responds within 2–6 seconds (1–2 blocks). On a production mainnet, this could be 12–30 seconds depending on KMS node availability and block times. Design your UX to show a "waiting for reveal..." state.

Async Decryption Security Checklist

ItemRisk if MissingFix
onlyGateway modifier Anyone can forge a callback with arbitrary plaintext Always verify msg.sender == GatewayLib.gatewayContractAddress()
allowForDecryption before request KMS cannot decrypt — request silently ignored Call in same tx or prior tx
Validate requestId in callback Replay or substitution of old results Map requestId → expected context and validate
maxTimestamp expiry Contract waits forever if KMS is down Set 1–7 day deadline; add fallback recovery path
Reentrancy guard in callback Callback could trigger re-entry during state update Use OpenZeppelin ReentrancyGuard or checks-effects pattern

QUESTION 01 / 06
Why is FHEVM decryption always asynchronous (two transactions)?
AIt's a design choice for gas efficiency
BThe EVM cannot execute WASM code in-block
CThreshold decryption requires consensus across multiple KMS nodes, which cannot complete within a single block's execution
DThe Gateway contract stores ciphertexts in a queue to batch decryptions
Correct — C. The KMS is a distributed MPC cluster. Each node must independently compute a partial decryption and the results must be combined. This consensus round spans network roundtrips and cannot fit inside one EVM execution context.
QUESTION 02 / 06
What is the consequence of omitting the onlyGateway modifier on a decryption callback?
AAny address can call the callback with forged plaintext values, completely bypassing the decryption security
BThe callback can only be called once
CGas costs increase
DThe function can only be called internally
Correct — A. Without onlyGateway, your callback is a public function. A malicious actor could call it directly with any plaintext values, for example setting a winning auction bid to 0 and claiming the prize without paying.
QUESTION 03 / 06
You request decryption of two handles in order: [yesVotes, noVotes]. What should your callback signature look like?
Acallback(uint256 requestId, uint256[] plaintext)
Bcallback(uint32 yesCount, uint32 noCount)
Ccallback(uint256 requestId)
Dcallback(uint256 requestId, uint32 yesCount, uint32 noCount)
Correct — D. The Gateway passes the requestId first, then the decrypted plaintext values in the exact same order as the handles array. Each plaintext is a separate parameter of its original Solidity type.
QUESTION 04 / 06
What happens if you call Gateway.requestDecryption without first calling TFHE.allowForDecryption(handle)?
AThe request succeeds but the callback receives 0 for that value
BThe KMS will not decrypt it — the ACL check fails and the request is ignored or reverts
CThe Gateway automatically grants the permission on your behalf
DThe transaction succeeds but emits no event
Correct — B. allowForDecryption is the ACL step that tells the on-chain ACL contract that the Gateway is permitted to decrypt this handle. Without it, the KMS's ACL check will reject the decryption request.
QUESTION 05 / 06
In the conditional reveal pattern, why must you make two separate Gateway calls (condition first, value second)?
ATo save gas by batching in two requests
BBecause the Gateway limits each request to one handle
CYou cannot branch on encrypted values in Solidity — you must first reveal the boolean condition as plaintext before deciding whether to reveal the value
DThe KMS processes two-step requests faster
Correct — C. In FHEVM, if (encryptedBool) is not possible — all branches must be oblivious. To gate a reveal on a condition, you must first decrypt the condition to plaintext via the Gateway, then use the resulting boolean in a normal Solidity if-statement to decide whether to proceed with the value reveal.
QUESTION 06 / 06
What is the recommended frontend pattern to know when a Gateway callback has executed?
AEmit a dedicated event in your callback function and watch it with watchContractEvent before triggering the request transaction
BPoll the contract's storage every 500 ms until the value changes
CWait for the request transaction to confirm — the callback is always in the same block
DCall a getDecryptionStatus(requestId) view function on the Gateway
Correct — A. Event-driven is the cleanest approach. Subscribe to your contract's callback event before sending the request transaction. When the callback executes (1–2 blocks later), the event fires and your UI updates. Polling is wasteful and introduces latency.
