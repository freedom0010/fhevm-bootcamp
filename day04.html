Why euint64 for Balances?

💡
euint64 Sweet Spot for Tokens
Standard ERC-20 uses uint256, but FHEVM encrypting 256 bits costs far more gas. euint64 (max ~1.8×10¹⁹) covers all practical token amounts with 18-decimal precision — e.g., 10⁹ tokens × 10¹⁸ decimals = 10²⁷, which would need euint128. For most tokens with capped supply under 10⁸ and 18 decimals, euint64 covers 10¹⁸ × 10⁸ = 10²⁶ — still too large. Use euint64 for tokens with supply ≤ 10 billion units (18 decimals), euint128 for larger.

The ConfidentialERC20 Contract

Storage Layout & Events

Soliditycontracts/ConfidentialERC20.sol (Part 1 — storage)
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@fhevm/solidity/lib/FHE.sol";
import "@fhevm/solidity/config/ZamaConfig.sol";

contract ConfidentialERC20 is ZamaEthereumConfig {

    // ── Token metadata ────────────────────────────
    string  public name;
    string  public symbol;
    uint8   public decimals = 6;    // use 6 to keep amounts in euint64 range
    address public owner;

    // ── Encrypted state ───────────────────────────
    // Encrypted balances: only owner + granted addresses can decrypt
    mapping(address => euint64) private _balances;

    // Encrypted allowances: spender → owner → amount
    mapping(address => mapping(address => euint64)) private _allowances;

    // Plaintext total supply — intentionally public (sum of all balances)
    uint64 public totalSupply;

    // ── Events (no amounts — privacy design) ─────
    event Transfer(address indexed from, address indexed to);
    event Approval(address indexed owner, address indexed spender);
    event Mint(address indexed to, uint64 amount); // mint amount is public

    constructor(string memory _name, string memory _symbol) {
        name   = _name;
        symbol = _symbol;
        owner  = msg.sender;
    }
}
⚠
totalSupply is Public — Is That OK?
Yes — the total supply of a token is typically not sensitive information. Hiding it would also break composability (AMMs, oracles). What matters is that individual balances are private. This design mirrors how real-world confidential asset systems work: the total float is public, individual holdings are not.

_mint() — Creating Tokens

SolidityConfidentialERC20.sol — mint
/// @notice Mint tokens to an address (owner only, plaintext amount)
/// Mint amount is public — this is a deliberate design choice.
/// The resulting balance remains encrypted.
function mint(address to, uint64 amount) external {
    require(msg.sender == owner, "Not owner");
    require(amount > 0, "Zero mint");

    // Convert plaintext amount to an encrypted handle
    euint64 encAmount = FHE.asEuint64(amount);

    euint64 current = _balances[to];

    if (euint64.unwrap(current) == 0) {
        // First mint: no existing balance, just assign
        _balances[to] = encAmount;
    } else {
        // Add to existing encrypted balance
        _balances[to] = FHE.add(_balances[to], encAmount);
    }

    // Grant ACL: recipient and contract can both access the new handle
    FHE.allowThis(_balances[to]);
    FHE.allow(_balances[to], to);
    FHE.allow(_balances[to], owner);   // owner can audit balances

    totalSupply += amount;
    emit Mint(to, amount);
}

/// @notice Returns the caller's encrypted balance handle.
/// Only authorized addresses (those with ACL grants) can call this.
function balanceOf(address account) external view returns (euint64) {
    require(
        msg.sender == account || FHE.isSenderAllowed(_balances[account]),
        "Not authorized to view balance"
    );
    return _balances[account];
}

transfer() — The Core Privacy Operation

This is the most complex function. We must handle three cases without branching on encrypted values: sender has enough funds, sender has less than amount (cap at balance), and maintaining both balances correctly.

SolidityConfidentialERC20.sol — transfer
/// @notice Transfer encrypted tokens. The amount is provided encrypted.
/// If amount > balance, the transfer is capped at the sender's balance.
/// (No revert — branching on encrypted bool is impossible.)
function transfer(
    address         to,
    externalEuint64 calldata encAmount,
    bytes           calldata proof
) external returns (bool) {
    require(to != address(0), "Zero address");
    require(to != msg.sender,  "Self-transfer");

    // 1. Validate input and get encrypted amount
    euint64 amount  = FHE.fromExternal(encAmount, proof);
    euint64 balance = _balances[msg.sender];

    // 2. Compute: can sender afford it?
    ebool canAfford = FHE.le(amount, balance);  // amount <= balance

    // 3. Actual transfer amount: min(amount, balance) — caps at balance
    //    FHE.select(cond, ifTrue, ifFalse)
    euint64 actualAmount = FHE.select(canAfford, amount, balance);

    // 4. Update balances (never reverts — FHE.select handles underflow)
    _balances[msg.sender] = FHE.sub(balance, actualAmount);
    _balances[to]         = FHE.add(_balances[to], actualAmount);

    // 5. Grant ACL for both new balance handles
    FHE.allowThis(_balances[msg.sender]);
    FHE.allow(_balances[msg.sender], msg.sender);
    FHE.allow(_balances[msg.sender], owner);

    FHE.allowThis(_balances[to]);
    FHE.allow(_balances[to], to);
    FHE.allow(_balances[to], owner);

    emit Transfer(msg.sender, to);    // no amount in event
    return true;
}
⚠
No Revert on Insufficient Balance
Unlike standard ERC-20, we cannot revert on insufficient funds — that would leak information (the attacker learns their balance is below the amount). Instead, we cap the transfer at the sender's balance using FHE.select(canAfford, amount, balance). The caller may send "0" if they had nothing. This is the standard confidential transfer pattern.

approve() and Encrypted Allowances

SolidityConfidentialERC20.sol — approve
/// @notice Approve a spender with an encrypted allowance amount
function approve(
    address         spender,
    externalEuint64 calldata encAmount,
    bytes           calldata proof
) external returns (bool) {
    require(spender != address(0), "Zero spender");

    euint64 amount = FHE.fromExternal(encAmount, proof);
    _allowances[msg.sender][spender] = amount;

    // Both owner and spender need access to the allowance handle
    FHE.allowThis(_allowances[msg.sender][spender]);
    FHE.allow(_allowances[msg.sender][spender], msg.sender);
    FHE.allow(_allowances[msg.sender][spender], spender);

    emit Approval(msg.sender, spender);
    return true;
}

function allowance(address tokenOwner, address spender)
    external view returns (euint64)
{
    // Only tokenOwner or spender may read the allowance
    require(
        msg.sender == tokenOwner ||
        msg.sender == spender   ||
        FHE.isSenderAllowed(_allowances[tokenOwner][spender]),
        "Not authorized"
    );
    return _allowances[tokenOwner][spender];
}

transferFrom() — Spending an Allowance

SolidityConfidentialERC20.sol — transferFrom
/// @notice Spend from an allowance.
/// Amount is capped at min(requestedAmount, allowance, senderBalance).
function transferFrom(
    address         from,
    address         to,
    externalEuint64 calldata encAmount,
    bytes           calldata proof
) external returns (bool) {
    require(to != address(0), "Zero address");

    euint64 amount    = FHE.fromExternal(encAmount, proof);
    euint64 allowance = _allowances[from][msg.sender];
    euint64 balance   = _balances[from];

    // Cap at allowance, then cap at balance
    ebool   withinAllowance = FHE.le(amount, allowance);
    euint64 cappedByAllowance = FHE.select(withinAllowance, amount, allowance);

    ebool   withinBalance = FHE.le(cappedByAllowance, balance);
    euint64 actualAmount  = FHE.select(withinBalance, cappedByAllowance, balance);

    // Update balance and reduce allowance
    _balances[from]                    = FHE.sub(balance,   actualAmount);
    _balances[to]                      = FHE.add(_balances[to], actualAmount);
    _allowances[from][msg.sender]      = FHE.sub(allowance, actualAmount);

    // ACL grants for all three updated handles
    FHE.allowThis(_balances[from]);
    FHE.allow(_balances[from], from);    FHE.allow(_balances[from], owner);
    FHE.allowThis(_balances[to]);
    FHE.allow(_balances[to], to);       FHE.allow(_balances[to], owner);
    FHE.allowThis(_allowances[from][msg.sender]);
    FHE.allow(_allowances[from][msg.sender], from);
    FHE.allow(_allowances[from][msg.sender], msg.sender);

    emit Transfer(from, to);
    return true;
}

Overflow & Underflow Safety

Standard Solidity 0.8+ reverts on overflow/underflow. In FHEVM, we cannot revert on encrypted conditions — instead we use the capping pattern consistently:

Transfer Underflow

FHE.le(amount, balance) returns encrypted bool. FHE.select(canAfford, amount, balance) caps actualAmount at the sender's balance. Result: sender's balance never goes negative.

Allowance Underflow

Same pattern in transferFrom: first cap at allowance, then cap at balance. The allowance decreases by exactly actualAmount — never more than the current allowance.

Mint Overflow

For minting, the totalSupply is plaintext and uses standard arithmetic. Encrypted balance addition cannot overflow euint64 in practice if total supply is bounded.

Why Not Revert?

Reverting on "amount > balance" would reveal that the sender's balance is below the requested amount — leaking private data. The cap-and-proceed pattern preserves privacy.

The Standard ACL Grant Pattern

Every function that creates a new handle must follow this pattern. Memorize it — you'll write it hundreds of times:

SolidityStandard ACL pattern after any FHE op
// After every FHE operation that creates a new handle:
_balances[addr] = FHE.add(_balances[addr], amount);

// 1. Contract must be able to use in future txs (REQUIRED)
FHE.allowThis(_balances[addr]);

// 2. The account owner can decrypt their own balance
FHE.allow(_balances[addr], addr);

// 3. Optional: grant audit access (e.g., contract owner, compliance)
FHE.allow(_balances[addr], auditor);

// 4. For allowances: both parties need access
FHE.allow(_allowances[tokenOwner][spender], tokenOwner);
FHE.allow(_allowances[tokenOwner][spender], spender);

Minting and Checking Balance

TypeScripttest/ConfidentialERC20.test.ts
import { ethers } from "hardhat";
import { expect } from "chai";
import { getFhevmInstance } from "./helpers";

describe("ConfidentialERC20", () => {
  let token: any, owner: any, alice: any, bob: any;

  before(async () => {
    [owner, alice, bob] = await ethers.getSigners();
    const F = await ethers.getContractFactory("ConfidentialERC20");
    token = await F.deploy("ConfCoin", "CONF");
    await token.waitForDeployment();
  });

  it("mints to alice; totalSupply updates", async () => {
    await token.connect(owner).mint(alice.address, 1000n);
    expect(await token.totalSupply()).to.equal(1000n);
  });

  it("alice decrypts her balance = 1000", async () => {
    const instance = await getFhevmInstance();
    const addr     = await token.getAddress();

    const handle = await token.connect(alice).balanceOf(alice.address);

    const { publicKey, privateKey } = instance.generateKeypair();
    const eip712 = instance.createEIP712(publicKey, addr);
    const sig    = await alice.signTypedData(eip712.domain, eip712.types, eip712.message);
    const reenc  = await instance.reencrypt(handle, privateKey, publicKey, sig, addr, alice.address);

    expect(instance.decrypt(addr, reenc)).to.equal(1000);
  });

  it("bob cannot view alice balance", async () => {
    await expect(token.connect(bob).balanceOf(alice.address))
      .to.be.revertedWith("Not authorized to view balance");
  });
});

8 questions · euint, ebool, eaddress
QUESTION 01 / 08
Why does the confidential transfer() cap at balance instead of reverting when amount > balance?
AReverting is not supported in FHEVM contracts
BGas optimization — revert is more expensive than FHE.select()
CReverting would reveal information: the attacker learns the sender's balance is below the amount, breaking privacy
DEVM does not support reverts inside FHE operations
Correct — C. If the contract reverted with "insufficient balance", the caller would learn that their balance is below the attempted transfer amount — leaking the private balance range. By capping silently, the contract reveals nothing about the actual balance value.
QUESTION 02 / 08
In transfer(), what does FHE.select(canAfford, amount, balance) return when the sender cannot afford the transfer?
AZero — the transfer is skipped entirely
BThe sender's full balance — the entire balance is transferred (capped, not zero)
CThe amount — the same value is used regardless of condition
DAn error handle that signals the operation to be retried
Correct — B. FHE.select(condition, ifTrue, ifFalse): when canAfford is false, it returns the ifFalse branch which is the sender's balance. So the entire remaining balance is transferred, not zero. This prevents underflow while ensuring the recipient always gets something meaningful.
QUESTION 03 / 08
The confidential Transfer event emits Transfer(from, to) without the amount. What metadata is still leaked?
ANothing — the transaction is fully private
BThe amount — it can be inferred from gas usage
CThe recipient's balance range
DThe sender and recipient addresses, the timestamp, and the fact that a transfer occurred — which is still meaningful on-chain metadata
Correct — D. Even without the amount, on-chain events reveal: who sent, who received, when, and that a transfer happened. This creates a transaction graph that can be analyzed. For truly private transfers you would need network-level privacy (Tor, etc.) as well. FHEVM hides amounts but not addresses.
QUESTION 04 / 08
Why must both the token owner AND the spender receive ACL grants on an encrypted allowance handle?
AThe spender needs to read the allowance to compute their remaining spending capacity; the owner needs it to manage (revoke/update) the allowance in future transactions
BBoth must sign transactions that modify the allowance
CThe KMS requires two-party authorization before decrypting allowance values
DACL grants are always applied in pairs by the FHEVM Executor
Correct — A. The token owner needs ACL access to be able to update or revoke the allowance (they need to read it to compute the new value). The spender needs it to be able to check their remaining allowance and pass the handle into transferFrom(). Without both grants, either party would fail their ACL check.
QUESTION 05 / 08
Why is totalSupply kept as a plaintext uint64 rather than being encrypted?
AFHEVM cannot add encrypted values to get a total
BEncrypting totalSupply would exceed the euint64 range
CTotal supply is not sensitive, composability with AMMs/oracles requires it to be readable, and hiding it would break price discovery
DPlaintext totalSupply is required by the ERC-20 standard
Correct — C. Total supply is an economic fact that needs to be public for markets to function. DeFi protocols, price oracles, and AMMs all need to know total supply. Encrypting it would prevent composability without providing meaningful privacy benefits — the total circulating amount is generally expected to be transparent.
QUESTION 06 / 08
In transferFrom(), you apply two sequential caps: first cap at allowance, then cap at balance. Why two separate steps?
AOne FHE.select() can only compare two values at a time — two steps are needed for three values
BEach constraint is independent: the spender may only use up to the authorized allowance, and the balance owner may only send what they have — both limits must be enforced separately
CThe coprocessor processes operations in sequential order and cannot combine comparisons
DIt is a gas optimization — a single three-way comparison costs more
Correct — B. These are two independent authorization constraints: (1) the spender can only spend up to what they were authorized (allowance cap), and (2) the token owner can only transfer what they actually have (balance cap). Both must be enforced separately because either could be the binding constraint depending on the state.
QUESTION 07 / 08
Why is decimals = 6 recommended for confidential tokens using euint64?
A6 decimals is the only value supported by the fhevmjs SDK
BHigher decimals increase the gas cost of FHE operations
C6 decimals is the ERC-20 standard for stablecoins
DWith 18 decimals, even 10 billion tokens would need ~10²⁷ storage — far beyond euint64's max of ~1.8×10¹⁹. Using 6 decimals means 1 token = 10⁶ units, keeping total supply well within euint64
Correct — D. With 18 decimals and any meaningful supply, you'd overflow euint64. With 6 decimals (like USDC), 10 trillion tokens worth would be 10¹⁸ — within euint64's range. If you need 18 decimals, use euint128 (max ~3.4×10³⁸), accepting the higher gas cost.
QUESTION 08 / 08
After calling FHE.sub(_balances[from], actualAmount) in transfer(), what is the minimum set of ACL calls needed?
AFHE.allowThis(_balances[from]) and FHE.allow(_balances[from], from)
BOnly FHE.allowThis(_balances[from]) — the address grant is optional
CNo ACL calls needed — FHE.sub() preserves existing grants
DOnly FHE.allow(_balances[from], from)
Correct — A. FHE.sub() creates a brand-new handle with zero ACL grants. At minimum: (1) allowThis() so the contract can use this balance in future transactions, and (2) allow(from) so the account holder can decrypt their own balance. Without allowThis(), the contract breaks on the next transaction. Without allow(from), the user can't see their balance.
