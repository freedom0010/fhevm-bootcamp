What is Fully Homomorphic Encryption?

Standard encryption protects data at rest and in transit, but computation requires decryption first. FHE breaks this constraint — it allows arbitrary computation directly on ciphertexts, producing results that, when decrypted, match what you'd get from operating on the plaintexts.

Dec( Enc(a) ⊕ Enc(b) ) = a + b
Homomorphic addition: operating on ciphertexts gives the same result as operating on plaintexts

The Core Intuition

Think of FHE like a locked mailbox with special gloves built in. Alice puts numbers into the box (encrypts), locks it, and hands it to Bob. Bob wears the built-in gloves to manipulate the contents inside the locked box — without ever seeing the actual numbers. When Alice unlocks the box, the result already reflects Bob's computation.

For smart contracts: users encrypt their inputs before sending them on-chain. The contract performs computation on ciphertexts via FHEVM, and no one — including validators and node operators — ever sees the plaintext values.

Three Fundamental Properties

Semantic Security
Two encryptions of the same plaintext produce different ciphertexts. An attacker cannot distinguish Enc(0) from Enc(1) without the secret key — even with unlimited computation.
Correctness
Homomorphic operations on ciphertexts produce the correct result when decrypted. Dec(Enc(a) + Enc(b)) = a + b holds with overwhelming probability.
Compactness
The ciphertext output size is bounded — it does not grow with the number of operations. This is what makes FHE "fully" homomorphic rather than "somewhat" homomorphic.
Post-Quantum Security
FHE hardness (Ring-LWE) is believed to resist quantum attacks. Unlike RSA or ECC, Shor's algorithm provides no effective speedup against lattice problems.

Why TFHE for Smart Contracts?

Smart contracts require fast per-gate evaluation. A simple ERC-20 transfer involves dozens of comparison and arithmetic gates on 64-bit values. With BGV or BFV, a single bootstrap already takes seconds — a transaction would never settle within a reasonable block time. TFHE's ~1 ms gate bootstrap makes non-trivial on-chain FHE feasible today.

TFHE also supports Programmable Bootstrapping (PBS) — it applies an arbitrary lookup table while refreshing noise, enabling efficient comparisons like gt, le, and non-linear functions at no extra cost over a regular bootstrap.

Ring-LWE Security Foundation

TFHE's security rests on the hardness of Ring Learning With Errors (Ring-LWE) — a variant of LWE that operates over polynomial rings for both security and efficiency.

The LWE Problem

Given a secret vector s, LWE samples look like:

b = <a, s> + e  (mod q)
a = random vector  |  s = secret key  |  e = small random noise  |  q = ciphertext modulus

The LWE assumption: given many (a, b) pairs, recovering s is computationally infeasible — even for a quantum computer. This is because LWE reduces to hard lattice problems (SVP, CVP) for which no efficient quantum algorithm is known.

Noise: The Double-Edged Sword

🔐 Noise Provides Security
The error e masks the secret key. Without knowing s, the value b is indistinguishable from random. This is what makes ciphertexts semantically secure.
⚠ Noise Limits Computation
Every homomorphic operation adds more noise. Once noise exceeds a threshold, decryption fails. Without bootstrapping, you can only do a bounded number of operations — "Somewhat Homomorphic Encryption" (SHE).

Bootstrapping: Unlimited Computation

Craig Gentry's 2009 insight: you can use FHE to homomorphically evaluate the decryption circuit itself. This refreshes the noise back to a small value, enabling arbitrarily deep computation.

How Bootstrapping Works

1

Noisy ciphertext c encrypting plaintext m

After several operations, ciphertext c still encrypts m but has accumulated noise approaching the decryption failure threshold.

2

Homomorphically evaluate the decryption circuit

Using an encrypted copy of the secret key, the bootstrapping procedure runs Dec(c) inside the FHE scheme itself — never touching the plaintext.

3

Fresh ciphertext — same plaintext, small noise

The output is a new encryption of m with small fresh noise. Computation can continue indefinitely by bootstrapping whenever noise grows large.

Programmable Bootstrapping (PBS)

🔑
TFHE's Key Advantage
TFHE performs bootstrapping at the gate level — every logical gate automatically includes a noise refresh. During this mandatory refresh, PBS lets you simultaneously evaluate any lookup table (LUT). This means comparisons like FHE.gt(a, b) cost the same as a basic gate — noise refresh and comparison happen in one operation. This is why FHEVM comparisons are gas-efficient.

The euintX Cost Model

In FHEVM, every encrypted integer type (like euint64) is implemented as a collection of TFHE boolean ciphertexts — one per bit. This directly predicts the relative gas cost of every operation.

💡
Mental Model: euintN = N TFHE Bit-Ciphertexts
A euint64 is 64 individual TFHE ciphertexts. Adding two euint64 values requires a 64-bit adder circuit — roughly 64 bootstrapping operations. A euint8 add uses ~8 bootstraps. Always use the smallest type that safely holds your value.

Exercise 1 — Homomorphic AND Gate

Verify the fundamental homomorphic property: compute a gate on encrypted inputs and confirm correctness after decryption.

Pythonex1_and_gate.py
from concrete import fhe

# Declare inputs as "encrypted" — compiler will generate FHE circuit
@fhe.compiler({"a": "encrypted", "b": "encrypted"})
def and_gate(a, b):
    return a & b  # bitwise AND maps to a single TFHE PBS gate

# All possible 1-bit inputs — compiler needs to know the input domain
inputset = [(0, 0), (0, 1), (1, 0), (1, 1)]
circuit = and_gate.compile(inputset)
circuit.keygen()  # generates secret key + evaluation key

print("Homomorphic AND gate:")
for a, b in inputset:
    enc_a, enc_b = circuit.encrypt(a, b)     # client-side encryption
    enc_r = circuit.run(enc_a, enc_b)        # server-side FHE computation
    result = circuit.decrypt(enc_r)          # client-side decryption
    ok = "✓" if result == (a & b) else "WRONG"
    print(f"  AND({a},{b}) = {result}  {ok}")

Exercise 2 — 4-bit Encrypted Adder

Build intuition for the bit-cost model. A 4-bit adder requires a ripple-carry circuit over 4 bit-ciphertexts — exactly what FHE.add(euint4, euint4) computes inside FHEVM.

Pythonex2_4bit_adder.py
from concrete import fhe

@fhe.compiler({"a": "encrypted", "b": "encrypted"})
def add_4bit(a, b):
    return (a + b) % 16  # 4-bit wrap: 15 + 1 = 0 (same behaviour as euint4)

inputset = [(i, j) for i in range(16) for j in range(16)]
circuit = add_4bit.compile(inputset)
circuit.keygen()

for a, b in [(5, 3), (15, 1), (7, 8), (0, 0)]:
    enc_a, enc_b = circuit.encrypt(a, b)
    result = circuit.decrypt(circuit.run(enc_a, enc_b))
    expected = (a + b) % 16
    print(f"  {a:2d} + {b:2d} = {result:2d}  (expected {expected})  {'✓' if result==expected else 'WRONG'}")

# Challenge: why does 15 + 1 = 0?  Same reason euint4 overflows in FHEVM.

Exercise 3 — Benchmark Bootstrap Time

Pythonex3_benchmark.py
from concrete import fhe
import time

@fhe.compiler({"a": "encrypted", "b": "encrypted"})
def gate(a, b): return a & b

circuit = gate.compile([(0,0),(0,1),(1,0),(1,1)])
circuit.keygen()
enc_a, enc_b = circuit.encrypt(1, 1)

times = []
for _ in range(20):
    t0 = time.perf_counter()
    circuit.run(enc_a, enc_b)
    times.append((time.perf_counter() - t0) * 1000)

avg = sum(times) / len(times)
print(f"Average TFHE gate: {avg:.2f} ms")
print(f"Estimated euint8 add: {avg*8:.0f} ms")
print(f"Estimated euint64 add: {avg*64:.0f} ms  ({int(64/8)}x more expensive)")
💡
What to observe
The linear relationship between bit-width and computation time is exactly the gas cost model in FHEVM. On Zama's coprocessor, hardware acceleration brings euint64 add under 100ms total. The ratio between types is what matters for contract design.

QUESTION 01 / 07
Why does FHEVM use TFHE instead of BGV or CKKS?
ACKKS does not support integer arithmetic at all
BTFHE bootstraps at ~1 ms per gate — fast enough for practical smart contract execution within block time
CBGV ciphertexts are too large to store on-chain
DTFHE is the only scheme that supports 256-bit integers
Correct — B. BGV and CKKS bootstrap in seconds — far too slow for on-chain use. TFHE's ~1 ms gate-level bootstrap makes it the only practical choice for smart contract FHE today. CKKS supports approximate floating-point arithmetic, making it unsuitable for exact financial arithmetic.
QUESTION 02 / 07
In the LWE sample b = <a, s> + e (mod q), what is the primary role of the noise term e?
AIt compresses ciphertexts to reduce storage size
BIt speeds up decryption by reducing computation
CIt masks the secret key, making (a, b) pairs computationally indistinguishable from random — providing semantic security
DIt adds to the plaintext to prevent integer overflow
Correct — C. Without noise, b = <a, s> mod q would be a system of linear equations trivially solvable by Gaussian elimination. The small error e makes the system computationally hard — this is the core security guarantee of LWE-based cryptography.
QUESTION 03 / 07
What does bootstrapping accomplish in a fully homomorphic encryption scheme?
AIt converts a ciphertext from one scheme to another
BIt reveals the plaintext to a trusted third party for verification
CIt compresses a ciphertext to reduce on-chain storage
DIt refreshes the accumulated noise in a ciphertext, enabling unlimited-depth computation without decrypting
Correct — D. Without bootstrapping, noise grows until it crosses the decryption failure threshold. Bootstrapping homomorphically evaluates the decryption circuit, producing a fresh ciphertext with small noise that still encrypts the same plaintext. This is Gentry's 2009 breakthrough that made FHE "fully" homomorphic.
QUESTION 04 / 07
A euint64 addition in FHEVM requires approximately how many TFHE bootstrapping operations?
A~64, because euint64 is 64 individual TFHE bit-ciphertexts computing a 64-bit adder circuit
BExactly 1, because the entire 64-bit value is stored in a single ciphertext
C~256, proportional to the security parameter size
D0, because addition does not require bootstrapping
Correct — A. In FHEVM's TFHE implementation, euint64 is 64 separate TFHE bit-ciphertexts. A 64-bit ripple-carry adder evaluates ~64 full-adder gates, each of which includes a bootstrap. This is why euint64 operations cost ~8× more than euint8 operations — it's 8× more bits.
QUESTION 05 / 07
Why is Ring-LWE considered post-quantum secure?
AIt uses elliptic curve groups that Shor's algorithm cannot efficiently attack
BIt reduces to hard lattice problems (SVP/CVP) for which no efficient quantum algorithm is known — Shor's algorithm does not apply
CThe key length of 4096+ bits is too long for any quantum computer to process
DQuantum computers cannot perform modular arithmetic
Correct — B. Shor's algorithm efficiently breaks RSA (integer factoring) and ECC (discrete log). However, Shor's provides no useful speedup for lattice problems like SVP. The best quantum approach (Grover's) gives only a quadratic speedup — not enough to break parameters used in practice.
QUESTION 06 / 07
You need to store an encrypted age value (0–150) in a smart contract. Which type gives the best gas efficiency?
Aeuint256 — always use the largest type to avoid overflow
Beuint16 — standard choice for small integers
Ceuint8 — holds 0–255, comfortably covers all ages, and has the lowest cost
Deuint32 — needed for future-proof compatibility
Correct — C. euint8 holds 0–255, more than covering human ages. At 2× baseline cost, it saves 4× vs euint16, 8× vs euint32, and 16× vs euint256. Always use the smallest type that safely holds your value range — this is the single most impactful gas optimization in FHEVM.
QUESTION 07 / 07
What makes TFHE's Programmable Bootstrapping (PBS) particularly valuable for smart contracts?
AIt allows bootstrapping to run across multiple CPU cores in parallel
BIt enables FHE computation on floating-point numbers
CIt is a paid cloud service for handling heavy bootstrap operations
DIt applies an arbitrary lookup table (LUT) during the noise-refresh step, enabling comparisons and non-linear functions at no extra cost beyond a regular gate
Correct — D. During TFHE's mandatory per-gate noise refresh, PBS simultaneously evaluates a programmable LUT — computing any function f(x) for free alongside the bootstrap. This makes comparisons like FHE.gt(), FHE.eq(), and min/max very efficient. Without PBS, comparisons would require expensive multi-gate circuits.
