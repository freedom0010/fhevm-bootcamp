ACL Deep Dive

The ACL contract lives at a fixed address set by your ZamaXxxConfig base contract. It maps (handle, address) → bool — a simple lookup that the coprocessor checks before honoring any FHE operation referencing a handle.

Complete ACL Function Reference

FunctionWho Can CallEffectPersists?
FHE.allow(handle, addr)Any contractGrants addr permanent read/use access to handle✓ Yes
FHE.allowThis(handle)Any contractShorthand: allow(handle, address(this))✓ Yes
FHE.allowTransient(handle, addr)Any contractGrants addr access for the current transaction only — revoked automatically at tx end✗ Tx-scoped
FHE.makePubliclyDecryptable(handle)Any contractMarks handle as decryptable by anyone via Gateway — IRREVERSIBLE✓ Permanent
FHE.isSenderAllowed(handle)Any (view)Returns true if msg.sender has ACL access to handleRead-only
⚠
makePubliclyDecryptable is Irreversible
Once you call FHE.makePubliclyDecryptable(handle), that ciphertext can be decrypted by anyone via the Gateway forever. There is no revoke. Use only for data you intend to reveal publicly (e.g., auction results, final vote tallies). Never call it on a handle that might need to stay private.

allowTransient — Cross-Contract Calls

When Contract A calls Contract B in the same transaction, Contract B needs access to handles owned by Contract A. allowTransient grants that access for the current transaction only — automatically cleaned up when the transaction ends.

SolidityallowTransient pattern for cross-contract calls
// Contract A — passes its encrypted data to Contract B
contract TokenVault is ZamaEthereumConfig {
    euint64 private _balance;
    address public  swapRouter;

    function initiateSwap(externalEuint64 calldata enc, bytes calldata proof) external {
        euint64 amount = FHE.fromExternal(enc, proof);

        // Grant swapRouter access for THIS transaction only
        // After tx completes, access is automatically revoked
        FHE.allowTransient(amount, swapRouter);
        FHE.allowTransient(_balance, swapRouter);

        // Now call swapRouter — it can use amount and _balance within this tx
        ISwapRouter(swapRouter).executeSwap(amount, _balance);
        // After this call returns: swapRouter's transient access is revoked
    }
}

// Contract B — receives transient access to handles from Contract A
contract SwapRouter is ZamaEthereumConfig {
    function executeSwap(euint64 amount, euint64 maxSlippage) external {
        // Can use amount and maxSlippage because allowTransient was called
        // These operations work within this transaction
        ebool acceptable = FHE.le(amount, maxSlippage);
        euint64 result    = FHE.select(acceptable, amount, maxSlippage);
        FHE.allowThis(result);  // grant SwapRouter permanent access to result
        // Note: SwapRouter does NOT need allowTransient on result
        // because result is a NEW handle created by SwapRouter itself
    }
}

Role-Based Access Control

For complex protocols, a flat owner/user model is insufficient. You need roles: admins who can configure, auditors who can inspect, users who can transact, and operators who can act on behalf of users.

👑 Admin

Can grant/revoke roles. Can configure contract parameters. Cannot decrypt user data unless explicitly granted.

🔍 Auditor

Receives permanent ACL grants on all encrypted handles. Can decrypt for compliance purposes. Cannot modify state.

👤 User

Receives ACL grant on their own handles. Can encrypt inputs, decrypt own data via re-encryption. Cannot see others' data.

⚙ Operator

User-delegated actor (e.g., a trading bot). Receives ACL grant from user for specific handles. Revocable.

🔨 Minter

Can call mint() with plaintext amounts. Receives ACL on newly minted encrypted handles.

🔒 Compliance

Like auditor but for regulatory reporting only. May receive transient access rather than permanent grants.

RBAC + FHE Contract

Soliditycontracts/RBACVault.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;
import "@fhevm/solidity/lib/FHE.sol";
import "@fhevm/solidity/config/ZamaConfig.sol";

contract RBACVault is ZamaEthereumConfig {

    // ── Roles as bytes32 constants (OpenZeppelin style) ──
    bytes32 public constant ADMIN_ROLE    = keccak256("ADMIN");
    bytes32 public constant AUDITOR_ROLE  = keccak256("AUDITOR");
    bytes32 public constant MINTER_ROLE   = keccak256("MINTER");
    bytes32 public constant OPERATOR_ROLE = keccak256("OPERATOR");

    mapping(bytes32 => mapping(address => bool)) public roles;

    // Encrypted balances: only owner + auditors can decrypt
    mapping(address => euint64) private _balances;

    // Set of registered auditors (get ACL grants on all new handles)
    address[] public auditors;
    mapping(address => bool) public isAuditor;

    event RoleGranted(bytes32 indexed role, address indexed account);
    event RoleRevoked(bytes32 indexed role, address indexed account);

    constructor() { roles[ADMIN_ROLE][msg.sender] = true; }

    modifier onlyRole(bytes32 role) {
        require(roles[role][msg.sender], "Missing role");
        _;
    }

    function grantRole(bytes32 role, address account) external onlyRole(ADMIN_ROLE) {
        roles[role][account] = true;
        if (role == AUDITOR_ROLE && !isAuditor[account]) {
            auditors.push(account);
            isAuditor[account] = true;
        }
        emit RoleGranted(role, account);
    }

    function revokeRole(bytes32 role, address account) external onlyRole(ADMIN_ROLE) {
        roles[role][account] = false;
        // Note: cannot revoke ACL grants on existing handles (see Revocation section)
        emit RoleRevoked(role, account);
    }

    /// @notice Mint with auditor grants on the new handle
    function mint(address to, uint64 amount) external onlyRole(MINTER_ROLE) {
        euint64 current = _balances[to];
        if (euint64.unwrap(current) == 0) {
            _balances[to] = FHE.asEuint64(amount);
        } else {
            _balances[to] = FHE.add(_balances[to], FHE.asEuint64(amount));
        }
        euint64 handle = _balances[to];

        // Standard grants
        FHE.allowThis(handle);
        FHE.allow(handle, to);

        // Grant all auditors access to new handle
        for (uint i = 0; i < auditors.length; i++) {
            FHE.allow(handle, auditors[i]);
        }
    }

    function balanceOf(address account) external view returns (euint64) {
        require(
            msg.sender == account ||
            isAuditor[msg.sender] ||
            FHE.isSenderAllowed(_balances[account]),
            "Not authorized"
        );
        return _balances[account];
    }
}

Delegated Decryption

Users can delegate access to their encrypted data to an operator (e.g., a trading bot, a DeFi protocol). This is done by calling FHE.allow(userHandle, operatorAddress) from the user's transaction.

Delegation Pattern

SolidityOperator delegation
// User delegates their balance handle to an approved operator
function delegateToOperator(address operator) external {
    require(roles[OPERATOR_ROLE][operator], "Not a registered operator");
    // Operator gets ACL access to this user's balance
    FHE.allow(_balances[msg.sender], operator);
    operators[msg.sender] = operator;
    emit OperatorDelegated(msg.sender, operator);
}

// Operator can now use the user's encrypted balance in strategies
// (but cannot arbitrarily decrypt it — only use it in FHE ops)
function operatorTransfer(
    address user, address to,
    externalEuint64 calldata enc, bytes calldata proof
) external {
    require(operators[user] == msg.sender, "Not user operator");
    require(FHE.isSenderAllowed(_balances[user]), "No ACL access");
    euint64 amount = FHE.fromExternal(enc, proof);
    // ... transfer logic ...
}

Cross-Contract ACL

The Transient Pattern for Composability

DeFi composability requires contracts to pass encrypted values to each other. The pattern is always: grant transient access before the external call, never after.

✗ Wrong — transient after the call
// ❌ Protocol B can't use handle — it was
// called BEFORE the transient grant
IProtocolB(pb).deposit(_balance);
FHE.allowTransient(_balance, pb);
// Too late! deposit() already ran
✓ Correct — transient before the call
// ✓ Grant first, then call
FHE.allowTransient(_balance, pb);
IProtocolB(pb).deposit(_balance);
// Protocol B can use _balance in its
// deposit() execution frame

Common ACL Pitfalls

SolidityACL pitfall catalog
// ❌ PITFALL 1: Missing allowThis after FHE op
// The new handle has ZERO grants — next tx on this handle will fail
_balance = FHE.add(_balance, amount);
// forgot: FHE.allowThis(_balance) ← contract can't use it next tx!

// ❌ PITFALL 2: Granting to address(0) — public by accident
FHE.allow(handle, address(0)); // ← Don't do this

// ❌ PITFALL 3: Checking ACL in a write function without modifying
// isSenderAllowed() passes but you still need to grant AFTER any FHE op
function updateScore(externalEuint8 calldata enc, bytes calldata proof) external {
    require(FHE.isSenderAllowed(_scores[msg.sender]), "No access");
    _scores[msg.sender] = FHE.add(_scores[msg.sender], FHE.fromExternal(enc, proof));
    // ❌ Missing FHE.allowThis(_scores[msg.sender]) !
    // The old grant checked above was for the OLD handle
    // The new handle from FHE.add() has no grants
}

// ❌ PITFALL 4: allowTransient on the wrong address
// Using 'address(this)' when you mean the called contract's address
FHE.allowTransient(handle, address(this)); // grants THIS contract, not the callee
ICallee(callee).use(handle);              // callee still has no access!

// ✓ CORRECT: pass the callee address
FHE.allowTransient(handle, callee);
ICallee(callee).use(handle);

The Revocation Problem

⚠
ACL Grants Are Not Revocable
Once you call FHE.allow(handle, addr), that address has permanent access to that specific handle. There is no revoke function.

Mitigation strategy: When you need revocable access, create a new handle via a trivial FHE op (e.g., FHE.add(balance, ZERO)) and only grant the new handle to current authorized parties. The old handle becomes inaccessible since the contract no longer stores it. The ex-operator still holds the old handle — but the contract has moved on to a new handle, so old access is moot.

This is why allowTransient is preferred for DeFi integrations — it automatically revokes.

Compliance Views

Regulated protocols need auditors or compliance officers to view encrypted balances. The pattern: maintain a separate auditor registry and grant all auditors access to every new handle.

SolidityCompliance auditor pattern
// Internal helper: grant all registered compliance viewers
function _grantCompliance(euint64 handle) internal {
    for (uint i = 0; i < complianceViewers.length; i++) {
        FHE.allow(handle, complianceViewers[i]);
    }
}

// Call at the end of every state-changing function
function deposit(externalEuint64 calldata enc, bytes calldata proof) external {
    euint64 amount = FHE.fromExternal(enc, proof);
    _balances[msg.sender] = FHE.add(_balances[msg.sender], amount);
    FHE.allowThis(_balances[msg.sender]);
    FHE.allow(_balances[msg.sender], msg.sender);
    _grantCompliance(_balances[msg.sender]); // auditors see new handle too
}

// Gas consideration: O(N) ACL writes per tx where N = auditor count
// For protocols with many auditors, consider a tiered approach:
// - Critical operations: full auditor grants
// - Routine ops: transient compliance access via external audit requests

Day 8 Quiz — Access Control Patterns
8 questions · select one answer each
QUESTION 01 / 08
Contract A calls Contract B in the same transaction, passing an encrypted handle. What must Contract A do before the call?
ACall FHE.allow(handle, addressB) for permanent access
BCall FHE.makePubliclyDecryptable(handle) so Contract B can read it
CCall FHE.allowTransient(handle, addressB) — grants access for the current transaction only, automatically revoked at tx end
DNothing — handle ownership is inherited by called contracts automatically
Correct — C. allowTransient is the correct pattern for cross-contract calls. It grants access only for the current transaction, then automatically revokes — perfect for DeFi composability where you don't want the called contract to retain permanent access to your users' data.
QUESTION 02 / 08
An auditor is removed from a role. Can you revoke their ACL access to handles they were previously granted?
AYes — call FHE.revoke(handle, auditor)
BNo — ACL grants are permanent. The mitigation is to generate a new handle (via a trivial FHE op) and stop granting the removed auditor on future handles
CYes — the admin can reset the ACL contract entries for that address
DYes — call FHE.allow(handle, auditor) again with a false flag
Correct — B. There is no revoke function in the FHEVM ACL. Once granted, an address has permanent access to that specific handle. The forward-looking mitigation: generate a new handle via FHE.add(balance, ZERO_HANDLE), grant new parties only, and stop referencing the old handle. The ex-auditor keeps their old grant but it becomes irrelevant.
QUESTION 03 / 08
You update an encrypted balance: _balance = FHE.add(_balance, amount). The old handle had an ACL grant for the user. Does the user still have access?
AYes — ACL grants transfer to the new handle automatically
BYes — the new handle inherits all grants from its input operands
CYes — the contract's allowThis covers all derived handles
DNo — every FHE operation produces a brand-new handle with zero ACL grants. You must re-run FHE.allow(newHandle, user) after every operation
Correct — D. This is the most common ACL bug. FHE.add() creates a new handle — it does NOT inherit the ACL grants of its inputs. You must explicitly re-grant all necessary addresses on the output handle. Forgetting this means the user can never decrypt their updated balance.
QUESTION 04 / 08
What is the correct order of operations when using allowTransient for a cross-contract call?
A1. Call FHE.allowTransient(handle, callee) 2. Call the external contract
B1. Call the external contract 2. Call FHE.allowTransient to retroactively grant
CThe order doesn't matter — transient grants apply to the entire transaction
D1. Call the external contract 2. Call FHE.allow 3. Call the contract again
Correct — A. allowTransient must be called BEFORE the external call. The transient grant needs to be active when the callee executes its FHE operations. Calling it after is too late — the callee has already run and failed its ACL check.
QUESTION 05 / 08
Why is FHE.isSenderAllowed(handle) used in view functions, while FHE.allow() should NOT appear in view functions?
AFHE.allow() requires a transaction signature that view functions can't provide
BFHE.isSenderAllowed() is cheaper than FHE.allow()
CFHE.allow() writes to the ACL contract (state change) — view functions cannot modify state. isSenderAllowed() only reads, which is valid in view functions
DView functions can't interact with external contracts like ACL
Correct — C. FHE.allow() writes to the ACL contract — it's a state-changing operation. Solidity view functions cannot modify state. isSenderAllowed() reads from the ACL contract, which is allowed. Put your allow() calls in write functions (the ones that modify encrypted state), use isSenderAllowed() in view functions to gate access.
QUESTION 06 / 08
In a protocol with 5 auditors, how many extra ACL writes does each transfer() call incur?
A0 — auditors receive bulk access via a single registry call
B10 — 5 auditors × 2 handles updated per transfer (sender balance + recipient balance) = 10 extra allow() calls
C5 — one grant per auditor for the transfer event
D2 — one for each balance handle, auditors share a single ACL slot
Correct — B. Each transfer() updates two balance handles (sender and recipient). Each new handle needs allow() for every auditor. With 5 auditors and 2 handles, that's 5×2 = 10 extra SSTORE operations per transfer, plus the standard allowThis + allow(user) grants. This is why managing auditor count matters for gas.
QUESTION 07 / 08
What does calling FHE.allowTransient(handle, address(this)) accomplish?
AGrants temporary access to the contract itself — useful for recursive calls
BEquivalent to allowThis() but only for the current transaction
CGrants the owner transient access to the handle
DMostly useless — if you need the contract to access its own handle, use FHE.allowThis() for permanent access. allowTransient to address(this) wastes gas because transient grants on the calling contract expire at tx end anyway
Correct — D. For cross-contract calls, you want allowTransient to the CALLEE address, not address(this). allowTransient(handle, address(this)) grants the current contract transient access to its own handle — which it should already have via allowThis(). It's redundant and wastes gas.
QUESTION 08 / 08
A user wants to let a trading bot manage their balance for one week, then revoke access. What is the best ACL design?
AUse a plaintext time-locked operator mapping. When the lock expires, generate a new handle via FHE.add(balance, ZERO) and do not grant the bot on the new handle — the old grant becomes moot
BCall FHE.allow() now and FHE.revoke() after one week
CUse makePubliclyDecryptable and let the bot monitor via Gateway
DUse allowTransient renewed on each transaction
Correct — A. Since FHE.revoke() doesn't exist, the workaround is: (1) grant the bot now, (2) after one week, generate a new handle via FHE.add(balance, ZERO_HANDLE) — this creates a fresh handle with no grants, (3) grant only the user on the new handle, (4) the bot retains its old grant but the contract now references the new handle, making the old grant irrelevant. This is the standard FHEVM pattern for time-limited access.
