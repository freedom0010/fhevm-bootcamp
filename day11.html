Frontend Integration

Smart contracts handle encrypted state on-chain — but users need a way to submit encrypted inputs and read their own private data. fhevmjs is the TypeScript SDK that bridges the browser to FHEVM: it fetches the network public key, encrypts user inputs with ZK proofs, and re-encrypts ciphertexts back to the user's wallet key for private viewing. Today you build a full React/Next.js frontend for your ConfidentialERC20.

What is fhevmjs?

fhevmjs is Zama's official JavaScript/TypeScript library for interacting with FHEVM from a browser or Node.js environment. It handles three responsibilities that your smart contract cannot do alone:

  • Encryption at input time — converts a plaintext number into an FHEVM-compatible ciphertext before it ever leaves the browser.
  • ZK proof generation — proves the ciphertext was honestly formed (no garbage inputs) without revealing the value.
  • Re-encryption for viewing — re-wraps a stored ciphertext under the user's ephemeral key so only they can decrypt and display it.
🔑
Security Model
The FHEVM network public key encrypts all inputs. Only the KMS (a threshold MPC cluster) holds the corresponding secret key. fhevmjs re-encryption creates a temporary keypair in the browser — the re-encrypted value is only readable by that session.

FhevmInstance

The central object is FhevmInstance. Once created, it caches the network public key and exposes the encrypt/reencrypt APIs. You should create it once per session and share it via React context.

Public Key Fetch Flow

1

App Starts

Call createInstance({ networkUrl, kmsContractAddress, aclContractAddress }).

2

SDK fetches FHE public key

Makes an RPC call to the node to retrieve the TFHE bootstrapping public key (~7 MB, cached in memory).

3

Instance ready

Returns an FhevmInstance you can use for all encrypt/reencrypt calls in this session.

const config: NextConfig = {

Client-Side Encryption

Before calling any FHEVM contract function that takes an encrypted argument, you must encrypt the plaintext value in the browser using the network public key. The result is a ciphertext plus a ZK proof that the input is well-formed.

Encrypting an Input & Generating ZK Proof

TypeScript
lib/encrypt.ts
import { createInstance } from 'fhevmjs'
import type { FhevmInstance } from 'fhevmjs'

let _instance: FhevmInstance | null = null

export async function getFhevmInstance(): Promise<FhevmInstance> {
  if (_instance) return _instance

  _instance = await createInstance({
    // The FHEVM node RPC endpoint
    networkUrl: 'https://devnet.zama.ai',
    // Deployed contract addresses on Zama Devnet
    kmsContractAddress:  '0x904Be0...YOUR_KMS_ADDR',
    aclContractAddress:  '0xFee8C0...YOUR_ACL_ADDR',
  })

  return _instance
}

/**
 * Encrypt a uint64 value for use as a Solidity euint64 argument.
 * Returns { handles: Uint8Array, inputProof: Uint8Array }
 */
export async function encryptAmount(
  value: bigint,
  contractAddress: string,
  userAddress: string,
): Promise<{ handles: Uint8Array; inputProof: Uint8Array }> {
  const instance = await getFhevmInstance()

  // Create encrypted input bound to this contract + user
  const input = instance.createEncryptedInput(contractAddress, userAddress)
  input.add64(value)               // encrypt as euint64
  const encrypted = await input.encrypt()

  return {
    handles:    encrypted.handles[0],   // bytes32 handle for the Solidity call
    inputProof: encrypted.inputProof,   // ZK proof bytes
  }
}
⚠
Binding is Critical
createEncryptedInput(contractAddress, userAddress) binds the ciphertext to a specific contract and sender. If you submit it from a different wallet or to a different contract, the ZK proof will fail on-chain and the transaction reverts.

Sending an Encrypted Transaction

TypeScript
components/TransferForm.tsx (excerpt)
import { encryptAmount } from '../lib/encrypt'
import { useWriteContract, useAccount } from 'wagmi'
import { TOKEN_ABI, TOKEN_ADDRESS } from '../lib/contract'

export function TransferForm() {
  const { address } = useAccount()
  const { writeContract, isPending } = useWriteContract()

  async function handleTransfer(to: string, amount: bigint) {
    if (!address) return

    // 1. Encrypt the amount in the browser
    const { handles, inputProof } = await encryptAmount(
      amount,
      TOKEN_ADDRESS,
      address,
    )

    // 2. Call transfer(address to, bytes32 encryptedAmount, bytes inputProof)
    writeContract({
      address: TOKEN_ADDRESS,
      abi: TOKEN_ABI,
      functionName: 'transfer',
      args: [to, handles, inputProof],
    })
  }

  return (
    <button onClick={() => handleTransfer(recipientAddr, 100n)} disabled={isPending}>
      {isPending ? 'Encrypting + Sending...' : 'Transfer'}
    </button>
  )
}

Re-encryption Pattern

Encrypted balances are stored on-chain as ciphertexts under the network public key. To display a user's balance, you need to re-encrypt it under a key the user controls. Re-encryption never decrypts the value on-chain — it simply re-wraps the ciphertext for the user's eyes only.

EIP-712 Permit Signature

The KMS requires proof that the user consents to the re-encryption. This is a standard EIP-712 signature over the contract address + their public key. fhevmjs handles the domain and type hash construction for you.

Full Re-encryption & Decrypt Flow

TypeScript
lib/reencrypt.ts
import { getFhevmInstance } from './encrypt'
import { useSignTypedData } from 'wagmi'
import { readContract } from 'wagmi/actions'

export async function getDecryptedBalance(
  contractAddress: string,
  contractAbi: any[],
  userAddress: string,
  signTypedData: (params: any) => Promise<string>,
  wagmiConfig: any,
): Promise<bigint> {
  const instance = await getFhevmInstance()

  // Step 1: Generate ephemeral keypair + EIP-712 permit signature
  const { publicKey, privateKey } = instance.generateKeypair()
  const { typedData } = await instance.createEIP712(publicKey, contractAddress)
  const signature = await signTypedData(typedData)

  // Step 2: Call balanceOf(address, bytes32 publicKey, bytes signature)
  const reencryptedHandle = await readContract(wagmiConfig, {
    address: contractAddress as `0x${string}`,
    abi: contractAbi,
    functionName: 'balanceOf',
    args: [userAddress, publicKey, signature],
  }) as bigint

  // Step 3: Decrypt locally using the ephemeral private key
  const plaintext = instance.decrypt(contractAddress, reencryptedHandle, privateKey)
  return plaintext
}
💡
Keypair Lifetime
Generate a fresh keypair per balance-fetch call. The ephemeral private key never leaves the browser and should be discarded immediately after decryption. Do not cache it in React state or localStorage.

useEncryptedBalance Hook

Wrapping the re-encryption flow in a custom hook makes it trivial to use in any component.

TypeScript
hooks/useEncryptedBalance.ts
import { useState, useCallback } from 'react'
import { useAccount, useSignTypedData, useConfig } from 'wagmi'
import { getDecryptedBalance } from '../lib/reencrypt'
import { TOKEN_ABI, TOKEN_ADDRESS } from '../lib/contract'

export function useEncryptedBalance() {
  const [balance, setBalance] = useState<bigint | null>(null)
  const [loading, setLoading] = useState(false)
  const [error, setError] = useState<string | null>(null)

  const { address } = useAccount()
  const { signTypedDataAsync } = useSignTypedData()
  const config = useConfig()

  const fetchBalance = useCallback(async () => {
    if (!address) return
    setLoading(true); setError(null)
    try {
      const val = await getDecryptedBalance(
        TOKEN_ADDRESS, TOKEN_ABI, address, signTypedDataAsync, config,
      )
      setBalance(val)
    } catch (e: any) {
      setError(e.message ?? 'Unknown error')
    } finally {
      setLoading(false)
    }
  }, [address, signTypedDataAsync, config])

  return { balance, loading, error, fetchBalance }
}

Common Errors & Fixes

ErrorCauseFix
WebAssembly.instantiate not allowed Next.js WASM not enabled Add asyncWebAssembly: true to webpack.experiments
Input proof verification failed Wrong contract or sender address in createEncryptedInput Ensure contractAddress and userAddress match the actual tx
ACL: not allowed Contract didn't call TFHE.allow(handle, address) Add ACL permission in your Solidity contract after storing the ciphertext
Signature mismatch on balanceOf EIP-712 domain mismatch Ensure contractAddress passed to createEIP712 matches the deployed address exactly
Module not found: fhevmjs Import in Server Component Add 'use client' directive — fhevmjs is browser-only

QUESTION 01 / 06
What does createEncryptedInput(contractAddress, userAddress) do beyond just encrypting the value?
AIt signs the ciphertext using the user's private key
BIt binds the ciphertext to a specific contract and sender, so the ZK proof is only valid for that exact combination
CIt uploads the ciphertext to the FHEVM node for storage
DIt requests a decryption permit from the KMS
Correct — B. The binding prevents replay attacks. A ciphertext encrypted for contract A cannot be submitted to contract B, and a ciphertext meant for wallet X cannot be submitted by wallet Y. The ZK proof includes the binding as a public input.
QUESTION 02 / 06
Why must fhevmjs be used in a Client Component in Next.js (with the 'use client' directive)?
AIt requires access to the filesystem which is only available client-side
BServer Components don't support async functions
Cfhevmjs relies on WebAssembly and browser APIs (like crypto.subtle) that are not available in Node.js server-side rendering
DIt needs to access the user's localStorage to cache the public key
Correct — C. The TFHE operations are implemented in WASM, and the keypair generation uses browser crypto APIs. These are unavailable during SSR. Always import and use fhevmjs only in Client Components.
QUESTION 03 / 06
In the re-encryption flow, what is the purpose of the ephemeral keypair generated by instance.generateKeypair()?
AIt is stored on-chain to allow future decryption requests
BIt replaces the user's wallet key for signing transactions
CIt is uploaded to the KMS so it can send the decrypted value back
DThe KMS re-encrypts the on-chain ciphertext under this public key; the private key decrypts it locally in the browser
Correct — D. The user never gets the original plaintext directly. The KMS re-encrypts under the ephemeral public key. The browser decrypts with the ephemeral private key. The private key should never be persisted.
QUESTION 04 / 06
What is the role of the EIP-712 signature in the balanceOf re-encryption call?
AIt proves to the KMS that the wallet owner consents to the re-encryption, preventing unauthorized parties from triggering re-encryption on someone else's balance
BIt pays for the gas cost of the decryption
CIt grants ACL permission in the on-chain ACL contract
DIt replaces the transaction signature when calling view functions
Correct — A. The EIP-712 permit is a consent mechanism. Without it, anyone could call balanceOf with an arbitrary public key and request the KMS to re-encrypt your balance to their key.
QUESTION 05 / 06
You encrypt a transfer amount with contractAddress = "0xABC" but accidentally deploy a new contract at "0xDEF". What happens when you submit the transaction?
AThe transaction succeeds but the amount is silently set to zero
BThe on-chain ZK proof verification fails and the transaction reverts
CThe ciphertext is decrypted and compared — it works if the value matches
DThe transaction is rejected by the wallet before it's broadcast
Correct — B. The ZK proof binds the ciphertext to the exact contract address. Submitting to a different contract causes the proof verification precompile to reject the input, reverting the transaction.
QUESTION 06 / 06
Which call is responsible for fetching the ~7 MB TFHE bootstrapping public key from the network?
Ainstance.generateKeypair()
Binstance.createEncryptedInput()
CcreateInstance({ networkUrl, ... })
Dinstance.createEIP712()
Correct — C. createInstance is async and performs an RPC call to fetch the FHE public key from the FHEVM node. This should be called once and the instance cached for the session. All subsequent operations are local.
