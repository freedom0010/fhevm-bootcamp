The Five-Component System

FHEVM offloads all heavy FHE computation away from the EVM. The EVM stays cheap and deterministic — it only manages permissions and emits events. Real ciphertext computation happens in a specialized off-chain network, with key management handled by a separate MPC cluster.

1. Host Chain (EVM)

The EVM executes Solidity logic, maintains the ACL contract (which records permissions for each encrypted handle), and stores handles — 32-byte identifiers that point to ciphertexts held off-chain. No actual ciphertext data ever enters on-chain storage.

When you declare euint64 private balance, the storage slot holds a single 32-byte keccak256 hash — not a ciphertext. The hash identifies the ciphertext; the ciphertext itself lives on the coprocessor.

2. FHEVM Executor (Precompile)

A special precompile at address 0x000...005d intercepts every FHE.* library call. For each call it:

  • Verifies the caller has ACL permission for all input handles
  • Computes a deterministic output handle: keccak256(inputs + opcode + nonce)
  • Emits an on-chain event (e.g., FHEAdd) for the coprocessor
  • Returns the output handle immediately — the EVM doesn't wait for computation

3. Coprocessor Network

An off-chain cluster holding the FHE evaluation key — a public key that allows computing on ciphertexts without decrypting them. The coprocessor monitors on-chain events, performs TFHE arithmetic on the actual ciphertext data, and stores results indexed by their handles.

🛠
Semi-Trusted Security Model
The coprocessor holds the evaluation key (can compute) but not the secret key (cannot decrypt). A compromised coprocessor can produce incorrect results — a correctness failure — but cannot learn any plaintext values. Its operations are auditable through the on-chain event log.

4. Key Management Service (KMS)

The KMS holds the FHE secret key, but split across multiple nodes using threshold multi-party computation (MPC). Decryption requires a quorum of nodes (e.g., 3-of-5) to cooperate — no single node can decrypt alone.

The KMS handles two types of decryption requests:

  • User re-encryption — re-encrypts a value under the user's own public key so they can decrypt locally without exposing the plaintext on-chain
  • Public decryption — produces a plaintext result that is delivered to a contract via a Gateway callback

5. Gateway (On-Chain Bridge)

A Solidity contract at a known address that bridges between on-chain decryption requests and the off-chain KMS. Contracts call Gateway.requestDecryption(...), and the Gateway emits an event. KMS nodes respond by calling back a function on the requesting contract with the plaintext result.

⚠
Always use onlyGateway on callbacks
Callback functions are ordinary public Solidity functions. Without the onlyGateway modifier, any address can call your callback with fabricated plaintext values. This modifier verifies msg.sender == Gateway address before accepting a result.

Step-by-Step: What FHE.add() Actually Does

1

Your contract calls FHE.add(handleA, handleB)

The FHEVM Executor precompile is invoked. It checks that msg.sender has ACL access to both handleA and handleB. If either check fails, the transaction reverts immediately.

2

Output handle is computed and returned synchronously

The executor derives: resultHandle = keccak256(handleA, handleB, "add", blockNonce). This is deterministic — the same inputs always produce the same handle. The handle is returned to your contract immediately in the same call frame.

3

FHEAdd event is emitted on-chain

The executor emits FHEAdd(handleA, handleB, resultHandle). The EVM moves on; it doesn't wait. This event is the coprocessor's signal to perform work.

4

Coprocessor computes off-chain (async)

The coprocessor retrieves ciphertexts for handleA and handleB, performs the actual TFHE addition (~64 bootstrapping ops for euint64), and stores the result ciphertext indexed by resultHandle.

5

Result is usable immediately for chaining — physical ciphertext available before next block

You can chain resultHandle into further FHE ops in the same transaction. Any decryption request against resultHandle will succeed once the coprocessor has processed the event — typically within milliseconds, always before the next block.

Solidity Annotated FHE.add() — what the EVM really does 
// What you write:
euint64 result = FHE.add(balanceA, balanceB);

// What the FHEVM Executor does (conceptually):
// 1. require(ACL.isSenderAllowed(balanceA), "No ACL access to balanceA")
// 2. require(ACL.isSenderAllowed(balanceB), "No ACL access to balanceB")
// 3. resultHandle = keccak256(balanceA, balanceB, "fheAdd", blockNonce)
// 4. emit FHEAdd(balanceA, balanceB, resultHandle)
// 5. return resultHandle   ← immediately, synchronously

// Off-chain, asynchronously, the coprocessor:
// 6. Fetches ciphertexts for balanceA and balanceB
// 7. Computes: ciphertexts[resultHandle] = TFHE.add(ct_A, ct_B)

// `result` holds a valid handle. You can use it in further ops this tx.
// The physical ciphertext is ready for decryption before the next block.

The ACL (Access Control List) System

The ACL is a Solidity contract that tracks which Ethereum addresses are permitted to use each handle. Before any FHE operation, the executor verifies that msg.sender appears in the ACL for each input handle. Without an ACL grant, the operation reverts.

ACL Function Reference

FunctionPersistenceRevocablePurpose
FHE.allow(handle, addr) Persistent No Grant addr permanent permission to use or decrypt this handle in any future transaction
FHE.allowThis(handle) Persistent No Required after every FHE op — grants the contract (address(this)) persistent access so it can reuse the handle in future transactions
FHE.allowTransient(handle, addr) This TX only N/A Temporary grant, expires when the transaction ends. Call immediately before passing a handle to an external contract
FHE.makePubliclyDecryptable(handle) Permanent & irreversible Never Anyone can now request decryption via Gateway. Cannot be undone. Always restrict with onlyOwner + time locks
FHE.isSenderAllowed(handle) Read-only query N/A Returns true if msg.sender has ACL permission — use in require() guards on getters

The Three ACL Bugs Every Developer Hits

🚧
Bug #1 — Missing allowThis() after FHE operations
Every FHE operation produces a brand-new handle with zero ACL grants. If you don't call FHE.allowThis(newHandle), the contract cannot use that handle in any future transaction — the ACL check will fail and revert. This is the single most common FHEVM bug.
✗ WRONG — fails on second call
function add(
  externalEuint64 calldata inp,
  bytes calldata proof
) external {
  euint64 amt = FHE.fromExternal(inp, proof);
  balance = FHE.add(balance, amt);
  // balance is a NEW handle — zero ACL grants!
  // Second call will REVERT on ACL check.
}
✓ CORRECT — always allowThis()
function add(
  externalEuint64 calldata inp,
  bytes calldata proof
) external {
  euint64 amt = FHE.fromExternal(inp, proof);
  balance = FHE.add(balance, amt);
  FHE.allowThis(balance);     // contract can reuse ✓
  FHE.allow(balance, msg.sender); // caller can decrypt ✓
}
🚧
Bug #2 — No allowTransient() before cross-contract calls
When passing a handle to an external contract, that contract needs ACL access before it tries to use the handle. Use allowTransient immediately before the external call.
✗ WRONG — recipient has no access
// External contract will revert — no ACL
IVault(vault).deposit(userBalance);
✓ CORRECT — grant transient first
// Grant access for this transaction only
FHE.allowTransient(userBalance, vault);
IVault(vault).deposit(userBalance);
🚧
Bug #3 — Unguarded makePubliclyDecryptable()
makePubliclyDecryptable() is a one-way door that can never be closed. Any caller can permanently expose the encrypted value. Always protect it with strict access control and time locks.
✗ WRONG — any user can expose the secret
function reveal() external {
  // Anyone can call this!
  FHE.makePubliclyDecryptable(result);
}
✓ CORRECT — guarded with access + time
function reveal() external {
  require(msg.sender == owner, "Not owner");
  require(block.timestamp >= deadline, "Too early");
  FHE.makePubliclyDecryptable(result);
}

KMS Async Decryption

Because the FHE secret key is held by multiple KMS nodes using threshold MPC, every decryption requires multiple network round-trips between nodes — making synchronous on-chain decryption architecturally impossible. The pattern is always: request → wait → callback.

The Four-Step Decryption Flow

1

Contract calls Gateway.requestDecryption(handles[], selector, value, deadline, passthrough)

Specifies which handles to decrypt, which callback function (selector) should receive the result, a deadline, and optional passthrough data. Can request multiple handles in one call.

2

Gateway emits EventDecryption(requestId, handles, ...)

KMS nodes monitor this event. They retrieve the ciphertext from the coprocessor and begin the MPC threshold decryption protocol.

3

KMS nodes perform threshold decryption (off-chain MPC)

A quorum of KMS nodes jointly decrypt the ciphertext. No single node sees the full secret key. The quorum assembles the plaintext. Time: typically under 2 seconds on mainnet.

4

Gateway calls your callbackFn(requestId, plaintext)

Your callback must have the onlyGateway modifier. Without it, anyone can call the function with fabricated values.

Complete Async Decryption Example

Solidity contracts/AsyncReveal.sol 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@fhevm/solidity/lib/FHE.sol";
import "@fhevm/solidity/config/ZamaConfig.sol";
import "@fhevm/solidity/gateway/GatewayCaller.sol";

/**
 * Demonstrates the complete async decryption pattern.
 * An encrypted score is stored, and the owner can request a public reveal.
 */
contract AsyncReveal is ZamaEthereumConfig, GatewayCaller {

    euint64  private encryptedScore;    // encrypted on-chain
    uint64   public  revealedScore;     // plaintext, set after reveal
    bool     public  isRevealed;
    address  public immutable owner;
    uint256  public  revealDeadline;    // reveal only after this time

    event RevealRequested(uint256 indexed requestId);
    event ScorePublished(uint64 score);

    constructor(uint256 _revealAfter) {
        owner = msg.sender;
        revealDeadline = _revealAfter;
        // Initialize with a known plaintext score (0 for demo)
        encryptedScore = FHE.asEuint64(0);
        FHE.allowThis(encryptedScore);
        FHE.allow(encryptedScore, owner);
    }

    // Owner submits the real score (encrypted, before reveal time)
    function submitScore(
        externalEuint64 calldata enc,
        bytes calldata proof
    ) external {
        require(msg.sender == owner, "Not owner");
        require(!isRevealed, "Already revealed");
        encryptedScore = FHE.fromExternal(enc, proof);
        FHE.allowThis(encryptedScore);
        FHE.allow(encryptedScore, owner);
    }

    // Step 1: request public decryption (only after deadline)
    function requestReveal() external {
        require(msg.sender == owner, "Not owner");
        require(block.timestamp >= revealDeadline, "Too early");
        require(!isRevealed, "Already revealed");

        // Must mark handle as publicly decryptable before requesting
        FHE.makePubliclyDecryptable(encryptedScore);

        euint64[] memory handles = new euint64[](1);
        handles[0] = encryptedScore;

        uint256 reqId = Gateway.requestDecryption(
            handles,
            this.revealCallback.selector, // ← callback selector
            0,                            // ETH value to send
            block.timestamp + 2 hours,   // request expires
            false                         // passthrough mode
        );
        emit RevealRequested(reqId);
    }

    // Step 2: Gateway calls this with the decrypted value
    // onlyGateway is CRITICAL — prevents fake result injection
    function revealCallback(
        uint256 /* requestId */,
        uint64  decryptedValue
    ) external onlyGateway {       // ← MUST have this modifier
        revealedScore = decryptedValue;
        isRevealed    = true;
        emit ScorePublished(decryptedValue);
    }
}

Day 02 Quiz — FHEVM Architecture
8 questions · handles, ACL, KMS
QUESTION 01 / 08
What does FHE.add(handleA, handleB) synchronously return to your Solidity contract?
AThe ciphertext result of the addition, stored in EVM memory
BA 32-byte handle — a deterministic keccak256 hash referencing the future ciphertext the coprocessor will compute off-chain
CThe plaintext sum, verified by a trusted oracle before returning
DA zero value placeholder that is updated once the coprocessor responds
Correct — B. The EVM only computes and returns a deterministic output handle (keccak256 of inputs + opcode + nonce) and emits an event. The actual TFHE computation happens off-chain on the coprocessor. The handle is immediately usable for chaining further FHE operations in the same transaction.
QUESTION 02 / 08
Why is synchronous on-chain decryption architecturally impossible in FHEVM?
ADecryption always exceeds the block gas limit
BThe EVM cannot return variable-length data to smart contract callers
CThe secret key is split across KMS nodes using threshold MPC — decryption requires multiple network round-trips between nodes, which cannot happen inside a synchronous EVM call frame
DCiphertexts are too large to fit in EVM memory
Correct — C. Threshold MPC requires multiple KMS nodes to cooperate over the network — at minimum two round-trips. This is fundamentally incompatible with synchronous EVM execution, where every operation must complete atomically within a single call frame.
QUESTION 03 / 08
You write balance = FHE.add(balance, amount); but forget FHE.allowThis(balance). What happens in the next transaction that tries to use balance?
AThe transaction reverts — the contract's address has no ACL permission for the new handle, so the FHE operation fails its access check
BThe balance handle is silently reset to zero
CThe new handle automatically inherits ACL grants from its input handles
DNothing — allowThis() is optional if the contract address is the deployer
Correct — A. Every FHE operation creates a brand-new handle with zero ACL grants. The contract address is not automatically added. Without allowThis(), the next transaction that calls any FHE operation with this handle will fail the ACL check in the FHEVM Executor and revert. This is the most common FHEVM bug.
QUESTION 04 / 08
When is FHE.allowTransient(handle, addr) the right choice instead of FHE.allow(handle, addr)?
AWhen granting permanent read access to a user wallet address
BWhen the handle is about to be publicly decrypted via the Gateway
CWhen the handle was created from a constant plaintext value
DImmediately before a cross-contract call, to give a called contract temporary access that expires at the end of the transaction — avoiding a permanent grant to an external contract
Correct — D. allowTransient uses EIP-1153 transient storage under the hood — the grant exists only for the duration of the current transaction. It's designed specifically for cross-contract handle passing where you want the called contract to use the handle without receiving a permanent ACL grant.
QUESTION 05 / 08
What is the coprocessor's exact security boundary?
AIt can both compute on and decrypt ciphertexts, but only when authorized by the ACL
BIt can compute on ciphertexts using the evaluation key, but cannot decrypt them — it does not hold the secret key, which stays in the KMS
CIt can decrypt ciphertexts but cannot perform arithmetic on them
DIt only routes messages between the EVM and KMS; it never touches ciphertext data
Correct — B. The coprocessor holds only the evaluation key, which enables computation on ciphertexts. The secret key (needed for decryption) lives exclusively in the KMS cluster. A fully compromised coprocessor can produce wrong computation results but cannot reveal any plaintext values.
QUESTION 06 / 08
Why is the onlyGateway modifier on callback functions security-critical?
AIt prevents the KMS from delivering the same decryption result twice
BThe Gateway uses a non-standard function call encoding that requires this modifier to decode
CWithout it, any Ethereum address can call the callback with a fabricated plaintext value and corrupt your contract's state with a false decryption result
DIt handles gas reimbursement for the decryption operation
Correct — C. Callback functions are ordinary public Solidity functions. Without onlyGateway, anyone can call them directly. An attacker could call revealCallback(requestId, 999999) and inject a false result. The modifier checks msg.sender == Gateway.gatewayContractAddress() to ensure only the legitimate Gateway delivers results.
QUESTION 07 / 08
What does FHE.makePubliclyDecryptable(handle) do, and what is the critical risk?
AIt permanently and irreversibly marks the handle so any address can request decryption via the Gateway — the plaintext will be publicly obtainable forever and this cannot be undone
BIt re-encrypts the ciphertext under a new public key for safe sharing
CIt adds the handle to a public registry visible in block explorers
DIt decrypts the value and stores the plaintext in contract public state
Correct — A. Once called, this action cannot be reversed. Any address can then request the plaintext from the Gateway at any time in the future. This function should only be used for values that are intended to become public (e.g., auction results after the auction closes) and must always be guarded by strict access control and time-based restrictions.
QUESTION 08 / 08
Which component holds the FHE evaluation key, and what does it allow?
AThe KMS — it allows threshold decryption across multiple nodes
BThe Gateway — it allows bridging decryption requests on-chain
CThe FHEVM Executor — it allows verifying ZK proofs from user inputs
DThe Coprocessor — the evaluation key enables computing on ciphertexts (add, mul, compare, etc.) without decrypting them
Correct — D. The coprocessor holds the FHE evaluation key — a public key in the TFHE scheme that enables homomorphic computation (addition, multiplication, comparison, lookup tables) without revealing the plaintext. The secret key (needed to actually decrypt) is held only by the KMS cluster, maintaining the security separation between computation and decryption.
